## 结论

优先验证：现有后台使用独立、最小业务权限的 PostgreSQL 连接，仅调用已有固定结算分派入口。不将另购服务器或独立 JWT 签发／推送／续期设施作为当前结算功能的前置条件。

独立原型已经完成真实 PostgreSQL 15.8 的密码登录／授权和财务场景验收，结果见文末。它不是已经接入网站的传输：真实登录链路组合、生产网络／授权、TLS、池化及正式安装尚未验证。保留原应用候选、SQL、来源指纹、签发原型与历史证据，不在旧已验收产物上直接修改。

必要的是：服务器核实真实用户及商户权限，数据库验证价格、积分、券、库存和原单，事务原子提交并防重复。独立签发域是为特定威胁模型提供更强隔离的办法，不是这些业务规则天然需要的一台额外服务器。

## 现有路径与可复用内容

现有应用先验证个人账号或商户／员工身份，再由服务端构造 principal／actor。新结算客户端用系统短期 JWT，经 PostgREST 调用 `public.faolla_checkout_runtime_v1(text,jsonb)`，该入口以固定 CASE 分派 46 项方法。

短期 JWT 在这里承担系统调用凭据，不是结算账本算法。已核验的 37 份固定来源中，函数体未发现 `request.jwt`、`auth.uid()` 或 `session_user` 依赖；另核验旧 047 SQL 与适配器也未发现这些依赖。这只是限定来源的静态结论，不覆盖其他数据库对象或真实连接鉴权。

37 份来源中的 24 个函数及 047 适配器的两个函数包含 `current_user` 权限检查。必须保留原 `SECURITY DEFINER` 分派器及其 NOLOGIN 执行角色，不把这些检查删除或误当作无需权限。该执行角色原有的 BYPASSRLS 不可转授给网站登录角色。

继续复用原单标识、请求摘要、锁／版本核验、积分及券扣还、库存、预约／订单账本、结果恢复与取消流程。传输替换不能变成业务 SQL 重写，也不能回退到旧收银扣减入口。

## 新候选的权限边界

1. 仅新增一个用途明确的数据库 LOGIN 角色，显式禁止 superuser、BYPASSRLS、CREATEROLE、CREATEDB、复制及不必要的继承。不授予执行角色成员资格；审计直接／间接成员关系和 SET ROLE 能力。仅设置 NOINHERIT 不足以阻止通过成员关系 SET ROLE。[PostgreSQL 15 角色成员关系](https://www.postgresql.org/docs/15/role-membership.html)
2. 显式业务授权仅包含目标数据库 CONNECT、必需 schema USAGE 和固定分派器 EXECUTE；没有业务表直接读写、永久业务对象 DDL、内部函数执行或创建公共对象权限。必须核验 PUBLIC、默认授权和其他已有函数的间接权限，不能只检查新增 GRANT。普通数据库连接仍可使用部分内建功能和目录，不能宣传为“完全不能执行其他 SQL”。本次真实测试确认新账号也继承 PUBLIC 的 TEMP 权限，能建本会话临时表／临时函数；这不等于业务权限。没有为此撤销全体已有账号的 PUBLIC 权限，原安全 search_path 和全限定函数调用必须继续防止临时对象劫持。[PostgreSQL 15 授权叠加规则](https://www.postgresql.org/docs/15/sql-grant.html)
3. 原分派器继续由 NOLOGIN 执行角色拥有，保留固定方法／参数校验、安全 search_path 和所有业务守卫。当前入口只允许原 runtime 角色，新 LOGIN 将改变精确 ACL 契约，必须另建来源候选及完整负例测试，不能放松旧断言蒙混通过。[PostgreSQL 15 SECURITY DEFINER 注意事项](https://www.postgresql.org/docs/15/sql-createfunction.html)
4. 应用只发一个固定、参数化的分派查询；客户端不得传 SQL、角色名、身份 principal 或任选函数名。原同源检查、已验证账号、员工权限、暂停／试点开关以及操作前后身份复核全部保留。
5. 仅使用已核实的本机受限连接或私有网络连接；不为此开放公网 5432。跨主机连接须正确验证 TLS 证书和主机名。实际可用路径、数据库登录认证和连接限制目前仍未知，不自行改网络或猜测配置。
6. 使用小且有上限的连接池，保持现有总截止时间和数据库锁等待／语句超时；超时不自动重提财务写入。连接中断／提交结果不明时保留原单号，通过原结果查询恢复，不能换 nonce 再扣一次。连接取消、失效连接丢弃、池复用和撤销需真实验收；NOLOGIN 不等于已断开旧连接。
7. 凭据只在受信服务端配置，前端不可见、不写进仓库或日志；无 service_role、旧 cashier 或签名秘密降级兜底。测试／生产明确隔离，不根据连接错误自动换另一条授权路径。

## 没有解决的风险

这不是对网站宿主 root 的隔离。若攻击者控制后台进程或主机，仍可能盗用允许的结算能力；分派器的 principal 参数来自受信后台，不能阻止失陷后台冒充其可构造的其他 principal。现有其他路径也仍使用管理级客户端，本次不宣称整个应用已最小权限化。

独立签发端也不自动解决全部业务滥用：网站在短期凭据有效期内仍拥有授权能力。如果目标是抵抗宿主管理员失陷，需要独立的身份／逐笔授权验证与执行边界，单独换一台签发机器不够。

网站非 root 运行、减少已有管理级客户端、密钥轮换与更强租户隔离应分别评估，不在本次审查中改变现有成功路径。如果不能把新连接限制到上述业务权限，或实际网络／身份条件不成立，则停止该候选，不使用高权限连接凑合上线。
