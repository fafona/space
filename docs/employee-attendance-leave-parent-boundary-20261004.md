## 为什么先检查此项

130–134批已验证独立请假／通知／待审页面，但实际父组件的拒绝状态如何影响已经展开的子页面，尚不能由独立子组件通过推断。此边界直接影响旧资料与迟到响应的显示，优先于继续增加功能入口。

只读核对发现：

- `MerchantAttendanceAdminPanel.tsx` 的 `LeaveLauncher.active` 只依赖其他工作区是否展开；父 `AttendanceAdminClient` 读取被拒绝时只清自己的 `result`，未把拒绝状态通知已展开的请假子组件。
- `MerchantAttendanceSelfPanel.tsx` 的请假与通知入口同样只受其他工作区门控；父 `AttendanceSelfClient` 明确拒绝后清除本人打卡结果，但没有使已打开的请假／通知结果失效。
- `MerchantEnterpriseManager.tsx` 的共用 `apiFetch` 透传响应，不处理任意子接口的401／403；其overview有自己的拒绝处理，但不能将一次admin／self接口拒绝等同于overview已经重新核验。外层Portal／AdminClient另有身份刷新路径，本批不据此断言全应用focus永远不能清理。
- 子页面各自有隐藏／卸载失效机制，但父页面发生错误并不等于子页面已经隐藏或卸载。服务端再次拒绝新请求，与浏览器清除以前已合法读取的资料是两个不同边界。

## 本地复现范围

使用实际 `MerchantAttendanceAdminPanel` 与 `MerchantAttendanceSelfPanel`，经原默认handler、安装SDK及service_role访问既有隔离PG15中的合成资料。认证服务、平台权益及浏览器回环传输仍为合成，不冒充真实Auth／Next或完整企业壳。

1. 原负责人先查看请假详情；仅在所属合成schema改换商户当前负责人，再点击父页重新读取，验证原admin RPC确实拒绝旧负责人，观察旧子详情是否残留。
2. 员工先打开本人请假／通知；仅在合成schema停用该企业成员，再点击父页刷新状态，验证原self RPC确实拒绝，观察子资料是否残留。
3. 选择一个已在撤权前获授权的子GET延迟交付，核对父拒绝之后是否仍回显。此项若未实际运行，不能写成已通过或已复现。
4. 所有权／员工状态恢复后只读复核；检查业务事实、通知已读与数据库基线未改变。没有浏览器业务POST、真实账号变更、生产连接、新集群、完整构建或截图录像。待确认编号和其他浏览器存储的修复后保留行为留待获准修复时验证，不把本轮没有写操作当作已验过待确认恢复。

脚本将“诊断成功复现”与“产品授权清理验收通过”分开报告。发现缺陷不算产品验收通过；修复前不使用增加测试数量来宣称完成。

## 修复不能简单绑定父页面ready状态

| 情形 | 当前语义 | 不应采取的处理 |
| --- | --- | --- |
| 成员停用、角色失效或当前负责人改变 | 原服务端拒绝相应请求 | 留着旧子资料继续显示，或让旧响应再次回填 |
| 普通打卡配置未启用 | self GET可能返回 `attendance_disabled`；请假仍有独立读取规则 | 永久禁止进入请假／通知 |
| worker单独停用 | self GET可返回 `attendance_access_denied`；122／125仍允许有效成员读取本人请假历史 | 将同一错误码当成所有子模块永久撤权 |
| 平台暂停新业务 | 授权历史读取和原收据核对仍允许 | 把暂停当退出、删除待确认编号或阻止所有历史访问 |
| 临时网络／503、限流、存储问题 | 不证明当前成员已撤权，也不证明旧操作未提交 | 偷偷重试写入、清原号或直接永久封锁子功能 |

代码依据：111 self RPC对settings、成员／角色、worker及原事实归属各自校验；122请假的 `w.active` 用于 `can_submit`，125通知读取也不要求worker仍active。单凭父 `phase === blocked` 不足以决定所有子模块权限。

## 待用户同意后才实施的方向

针对已经确认的父读取拒绝，增加明确的子页面失效通知／代次：清除已展开的请假／通知结果和未保存草稿，阻止此前在途响应回显；保留已保存的申请、决定、事实及所有待确认操作编号。保留入口，用户重新打开时仍由该模块自己的接口重新核验，不要求普通打卡状态先恢复成功。

父客户端目前没有可供页面使用的结构化拒绝事件，不能解析中文提示文字或把 `blocked` 当权限标记。Admin客户端还会将不在自身错误目录中的认证拒绝归一为通用失败；新增分类应只用于当前代GET的子显示失效，不扩用到原POST的首次拒绝清编号逻辑。Self的拒绝也只能证明应重新核验，不能据此永久禁止独立历史读取。

具体拒绝分类、恢复及同时打开多个子页的清理范围须在修复契约中冻结；不在本次诊断顺手更改全站apiFetch、旧SQL或权限规则。按 `PROJECT_RULES.md` 第4条，此修改影响原成功父页面、草稿和恢复行为，需先向用户说明并取得同意。诊断完成不等于修复获准或已部署。
