# 第208批：事后采用实际页面、原号恢复与并发验收

2026-10-06，继续已批准的[203范围](employee-attendance-posthoc-adoption-boundary-20261006.md)，验收[207正式决定、本人结果与周期兼容](employee-attendance-posthoc-formal-review-20261006.md)的实际父页面及并发边界。本批修复两处页面缺口，完成下述限定本地闭环。**未部署、没有真实账号或手机验收，不代表整个考勤计划完成。**

## 发现及修复

### 关闭功能后仍能明确核对采用原编号

原采用子页按商户、操作者、人员和排班保存精确的待确认编号，但其父页入口只识别正式异常的待确认编号。关闭功能、隐藏或卸载子页后，父页丢失目标；正常入口又依赖当前正式异常详情。因此采用操作即使保留了原编号，也可能没有可达的恢复入口。

在[原异常工作区](../src/components/enterprise/MerchantAttendancePlanExceptionWorkspace.tsx)增加负责人“按已知人员／排班核对采用原号”入口，输入已知的人员与排班编号后进入[采用工作区](../src/components/enterprise/MerchantAttendancePlanPosthocWorkspace.tsx)的只读恢复模式：

- 严格核验两个编号，只读取当前商户、本人、人员与排班对应的精确本地键；不枚举其他身份的待确认内容。
- 不要求先取得174正式详情，不自动请求；只有明确点击“只核对原编号”才发起171恢复GET。
- 页面只保留返回与原号核对，不提供重新采用、撤销、编辑或重发POST。服务器仍独立鉴权；界面入口不是越权恢复通道。
- 缺少原编号、404或结果不明时不猜测成功，也不删除其他目标的编号；迟到回复、隐藏和身份范围变化仍清除可见正文。
- 普通员工在功能关闭时不新增此负责人入口。原成功路径和正常写入条件不变。

这不是跨设备恢复：用户仍须知道人员／排班编号，并保有原标签页的对应sessionStorage。丢失浏览器本地状态时，不通过扫描其他员工或伪造新操作来替代核查。

### 新说明不能被“已读”当成已经处理

正式决定后，员工新增本人说明会推进案件版本，但不改变出勤来源指纹；所以`stale=false`不代表没有待处理说明。本批新增“该决定之后有新的本人说明，尚待负责人再次处理；已读不会代替处理或周期确认”的提示，由案件版本与最新决定版本判断，不依赖有限历史列表是否包含全部旧说明。

没有改变SQL的陈旧定义、审批口径或周期规则。实际验收确认：员工明确业务已读和消息标读之后，负责人仍能看到新说明提示，周期仍有`unresolved_review`阻断。采用保存成功的文案也改为提示明确返回异常核查并另存正式结论，不再错误声称尚未接线。

## 实际页面验收

[208原生入口](../scripts/merchant-attendance-plan-posthoc-acceptance-native.mjs)复用唯一已有合成PG15，通过[回环HTTP桥](../scripts/fixtures/attendance-plan-posthoc-browser.mjs)加载真实AdminPanel／SelfPanel和真实处理器、服务、SQL；[浏览器验收器](../scripts/fixtures/attendance-plan-posthoc-browser-acceptance.mjs)使用独占的新建无头Chromium上下文。

电脑操控工具初始化失败，未控制用户已有Chrome或反复要求用户安装。本批改用项目现有Playwright执行普通自动化测试，没有新增依赖。认证为严格限域的合成认证，390px只是窄屏视口，**不是实际登录、手机定位或实体设备验收**。

8组页面流程通过：

1. 默认关闭的新入口、原父页列表与详情、当前失效依据的禁用状态及390px布局；打开入口不自动保存或重复读详情。
2. 负责人明确只读预览、读取候选、选择来源、填写理由，取消离开保留草稿；真实采用保存后截断成功响应，保留精确原编号。
3. 关闭采用及正式异常功能、重挂父页后，通过已知人员／排班进入只读恢复；不先读取174详情，只发一次171 GET，取得原回执并清除对应待确认键。
4. 重新开启后读取当前来源，明确保存正式决定；截断响应后关闭新写功能，按原号GET恢复，不重复保存或通知。
5. 本人读取保存决定，不冒充已重新核查当前依据；输入新说明时禁用已读，明确提交说明后再明确业务已读。
6. 业务已读不把事件消息标读；沿真实消息入口读取后，独立明确标记消息已读。
7. 挂起GET后隐藏页面或切换负责人／本人父页，释放旧回复不会恢复旧详情；重新显示不会自动查询。
8. 负责人重新读取后，新说明和待再次处理提示仍在，旧决定编号不变；真实周期只读采集保持未解决核查阻断。

共28次业务请求：23 GET、5次明确POST（采用、决定、说明、业务已读、消息标读各一次）。两次成功响应丢失；GET均核对事实哈希无写入，0外网请求、0页面错误、0桥接拒绝，未改无关localStorage／sessionStorage键。测试结束关闭浏览器、HTTP服务并恢复临时环境变量。
