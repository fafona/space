# 结算签发：独立安全域方案与隔离验证

## 结论与本轮范围

采用“独立签发端主动推送短期凭据，网站只接收凭据”的方向；不改变现有网站运行身份，不给网站通用签名 API 或私钥。本轮交付的是协议原型、受控隔离演练和落地计划，**不是正式安装或上线完成**。

用户批准 `call_8699ec11fd6442398d40e29367ba12a8` 仅覆盖本地方案和隔离验证：不购买或创建正式资源，不访问正式环境或密钥，不创建正式目录、角色、服务，不安装、部署或启用 Stripe。临时 CI 自有容器、内部网络、合成证书及密钥只用于演练；与正式环境无连接。

前次已批准的元数据采样确认指定网站进程以 UID/GID 0 运行；本轮引用已保存证据，不重新采集。`0700/0600` 不能隔离同机 root。既有网站成功路径、应用候选、续发控制器、38 步 SQL、v2 来源清单和原安装守卫保持不变。

## 1. 信任边界

```text
受信控制面：固定来源/固定接收者/生命周期审批
                    │
独立签发域：固定 claims → 私钥签发 → 主动 mTLS 推送
                                           │
现有网站域：公钥校验的接收器 → 原子凭据文件 → 固定结算 RPC
                                           │
独立执行边界：验签 + issuer/audience/role/期限校验 → 原有账本/幂等守卫
```

“独立执行边界”必须不能被受威胁的网站 root 改写。图不是声称现网已经具有这些独立边界。

| 对象 | 应持有 | 不应持有/开放 |
| --- | --- | --- |
| 独立签发端 | 私钥或受限签名提供者权限；固定来源、claims、接收者和续发策略 | 面向网站的任意 claims、任意 role、任意 URL 或通用 `/sign` 接口 |
| 网站侧接收器 | 短期 JWT、公钥、仅服务端身份的 TLS 私钥；固定签发端身份 | JWT 签发私钥、签发端 mTLS 客户端私钥、共享签名密钥 |
| 最终验证端 | 公钥和固定验证规则、最小数据库分派权限 | 应用可修改的信任根、算法选择或权限提升入口 |
| 受信运维/恢复端 | 来源和恢复证据、经审批的配置及生命周期权限 | 暴露给网站的签发控制命令、共享宿主 root/容器控制面凭据 |

同机容器、不同 Unix 用户、私有目录，均不能单独证明对宿主 root 的隔离。落地建议使用不同主机或真正隔离的托管运行域，同时隔离管理凭据、宿主挂载、部署代理和控制面。仅把私钥放进 KMS，却让网站拥有任意签名权限，也不满足本方案。

### 必须先确认的验证端条件

现有保存证据只证明 Auth/REST 存在 secret 环境项，没有读取其值，也没有证明实际 JWT 算法、key ID、密钥相同或验证能力。

- 原型只接受公私钥分离的配置；测试使用 EdDSA，**不代表为生产选择 EdDSA**。
- 如果 HMAC 验证秘密仍能被网站 root 读取，网站也能伪造令牌；迁走签发进程不能消除该风险。
- 即使用公钥，若网站 root 能改最终验证配置、数据库角色或直接使用更宽权限连接，仍可能绕过这条新边界。现有广权限凭据和同宿主控制权不在原型的保护承诺内。
- 不自动修改现有 Auth、Kong、PostgREST 或数据库权限。正式算法/公钥信任方案及独立执行边界需单独确认和验证；不能从合成测试反推现网兼容。

JWT 的算法、签发者、受众和令牌用途必须由验证端固定，不能由未验证的 header/claims 决定；参考 [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)。

## 2. 协议原型交付

`scripts/member-checkout-isolated-delivery.mjs` 是独立原型，无监听器、密钥加载器、环境选择、数据库入口或部署器。

- 保持原 `faolla-checkout-runtime-v1` envelope、固定 `faolla_checkout_runtime` 角色及原文件验证器；额外要求外层 generation 与签名内 jti 一致。
- 原型 TTL 上限仍为 300 秒；演练使用 30 秒。交付前保留原 12 秒调用预算和期限余量，不延长财务写请求。
- 签发端固定接收者；受信传输适配器进行 TLS 验证及公钥/证书身份固定。接收者不取自消息或用户 URL，不跟随重定向。
- 接收端先验证签名和 claims，再用原文件发布器原子替换、fsync、重读。确认回执绑定接收者、generation 和完整 envelope 摘要，不含 JWT 或私钥。
- 同 generation 同字节可幂等确认；同 generation 不同字节拒绝。新 generation 的签名 iat 必须前进；并发接收拒绝，避免文件发布竞争。
- 超时、丢回执或模糊发布后停止该发布器/接收器，不自动重发。受信控制面需先核对，才能明确启动新发布器并交付全新 generation；这不是重试财务操作。
- 过期令牌不延时，不降级为 service-role 或长期令牌，不因签发服务故障绕过原结算校验。停止签发不能即时撤销已发令牌；有效令牌仍可能被使用到期限结束。期限语义见 [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1.4)。

TLS/验签/文件发布依赖是受信适配器，不能把调用者提供的 `peerFingerprint` 字符串当成真实传输认证。演练从 TLS socket 获取真实证书摘要，并同时校验证书链、服务名和固定摘要。

## 3. 隔离演练方法与诚实上限

独立工作流 `.github/workflows/member-checkout-isolated-domain.yml` 只在本任务验收分支执行，使用 Linux、Node 24.13.1、随机 owner 标签的内部 Docker 网络及三个一次性容器。

三个角色是：独立私钥签发器、以 root 运行但没有签发材料的网站接收器、只持公钥的独立验证器。无生产网络、宿主目录绑定、公开端口或 Docker socket；根文件系统只读、去除 capabilities、禁止提权。生成的 TLS 材料随自有临时目录清理，报告不保存 JWT/私钥。

演练验证的重点包括真实 mTLS 推送、既有原子文件交付、root 无法读取另一个容器私钥/调用不存在的签名 API、错误客户端身份拒绝、网站 root 可改自己的凭据文件但伪造被独立验证端拒绝、丢回执不自动重发、明确恢复后用全新代次续发，以及停止签发后的真实时间过期拒绝。

本演练共享受信 CI 宿主和 Docker daemon，所以**不证明宿主管理员隔离**；验证器不是 PostgREST，网站角色不是 Next，签发器不是既有续发控制器，也没有完整财务写入。不能把它计入原 524 个应用场景或宣称现网端到端结算已通过。

原型接收水位仅在内存中（`persistentWatermark:false`）。整进程重启、全机丢失、独立密钥备份/轮换、公钥撤销、持久来源绑定及灾难恢复均未由本演练覆盖。文件权限只保护正常进程间交付，不冒充 root 安全边界。

## 4. 正式落地前的最小工作顺序

1. 确认独立签发域的位置和管理主体，以及最终验签/数据库授权是否能处于网站 root 无法改写的边界。先列资源和影响，不自动购买、创建或迁移。
2. 用另行批准的限定方法确认实际算法/issuer/audience/key ID 的配置来源，选择与真实网关兼容的公钥验证/隔离方案。不导出旧密钥进行比较，不回退为共享签名秘密。
3. 明确单接收者绑定、mTLS 身份、网络 ACL、期限/轮换/暂停策略，以及持久签发来源、水位、丢回执核对和独立恢复。时钟异常停止签发，不自动放大时间容差。
4. 为现有续发控制器增加经审查的传输衔接及生命周期验收：启动/续发/停止/超时/重启；不得因新发布器停止而无限循环签发。先补真实网关、最小角色和固定 RPC 验证，再申请正式安装。
5. 把获批配置和来源绑定到原安装 prepared/confirmation、locator 和备份恢复证据。原 inode/来源/权限守卫继续保留；全机重建需要单独可审计恢复流程，不重造或覆盖旧证据。
6. 明确安装/授权/服务变更与回滚清单后另行批准，再执行独立候选、完整 CI、备份和无维护验收。新单保持关闭，先验证原单核对与失败恢复；不改历史客户记录。
7. 选择获批商户验证预约/产品、积分、有效券、取消退还和后台付款状态，最后才接 Stripe/webhook。抽成、正式价格及自动续费选择尚未确认的部分不能自动启用收费。

这是一条收敛路线，不是新的正式访问许可。已确认的网关绑定、应用身份和数据库基线不重复采集；真正新增的事实/写入才列入下一次明确请求。
