# 员工业务权限安全契约

## 范围

负责人只能把以下业务菜单权限授予员工角色：积分兑换、预约管理、订单管理、会话和会员管理。企业管理沿用现有协作权限模型。未出现在权限目录中的负责人功能不能授予员工；没有服务端实现的叶权限也不能出现在角色编辑器中。

## 授权不变量

- 业务权限默认关闭。只有 `MERCHANT_STAFF_BUSINESS_RBAC_MODE=enforce` 且当前八位站点 ID 位于显式 allowlist 时，员工业务入口才启用。
- 员工请求只接受 Faolla 企业 Portal 的显式访问令牌。员工令牌不能回退到负责人 Cookie、个人账号 Cookie、浏览器持久化身份或可修改的用户 metadata。
- 负责人兼容路径只由数据库中的精确站点所有权授权；员工角色名称、前端菜单和客户端缓存都不是授权依据。
- 每个业务 API 都重新校验当前站点、员工状态、角色状态、员工与角色版本、模块 entitlement 和所需叶权限。跨站点、重复站点参数、无效依赖权限一律失败关闭。
- 客户资料、账户数据、导出、日历凭证和 Faolla 官方支持会话按独立敏感权限投影；没有对应权限时服务端先脱敏，不能只靠前端隐藏。
- 员工响应与错误均为 `private, no-store`；员工缓存仅限当前 React 内存，站点、principal、授权版本或权限变化必须卸载相关组件并清空内存数据。

## 写入与撤权语义

订单、预约、商品／兑换目录、会员账户、会话和对象上传在各自写队列或每次真实存储写入之前执行 fresh reauthorization。该检查是当前架构的授权线性化点：

- 若撤权在该检查之前完成，请求必须失败且不得开始业务副作用。
- 已经通过该检查的在途操作可以完成；撤权不追溯取消已经开始的本地写、邮件或对象存储调用。
- 对象上传在后续检查或上传失败时必须尽力清理本请求已经写入但尚未发布的对象。

这不是数据库级“撤权返回后零在途提交”保证。实现后者需要把员工／角色版本校验与每个 canonical DB 写放进同一事务 RPC，把邮件改为授权事务内 outbox，并用私有暂存加原子发布处理对象。不得用带 TTL 的应用层 mutation lease 冒充该保证，因为进程崩溃、租约过期和连续续租会造成旧写落地、撤权阻塞或撤权饿死。

`orders.view` 和 `bookings.view` 包含打开记录时同步“已读／已查看”时间；它们不能修改订单或预约的业务内容。其他状态、内容、邮件、导出、目录和账户变更均需要独立叶权限。

## 发布门禁

1. 数据库迁移、权限目录、负责人写角色 RPC 和运行时代码必须使用同一份权限集合及依赖关系。
2. 部署配置默认 `off`；生产 `enforce` 必须使用 `https://launch.faolla.com` 和非空、去重、最多 50 个八位站点 ID。
3. 新 rollout 必须绑定同一提交 SHA 的普通账号授权 readiness 与负责人数据库身份覆盖检查。
4. 先部署保持 `off`，再只对白名单测试站点启用；通过负责人回归、员工正向／越权／撤权、跨租户、缓存和审计验证后逐站扩大。
5. 任一权限异常、登录异常或数据泄漏迹象都先切回 `off`。关闭员工业务 rollout 不得影响企业协作、负责人现有菜单或个人／公开业务流程。
6. 首次上线必须作为兼容发布保持 `off`；此时服务端禁止创建或保留任何业务权限，只允许负责人显式剥离已有业务权限。只有上一份可回滚 release 已能解析 39 项新权限后，后续发布才可对精确站点白名单切换为 `enforce`。
7. 从 `enforce` 回滚到不认识新权限的旧版本前，必须先切回 `off`，逐站点显式剥离全部角色中的 39 项业务权限并验证数量为零，再启动旧版本。不得让自动回滚越过这项数据库兼容性检查。
