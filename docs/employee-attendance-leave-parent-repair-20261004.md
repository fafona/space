# 第136批：请假父子页面授权清理修复

日期：2026-10-04。用户在第135批诊断及影响说明后回复“好的，继续”，同意下述范围。已完成限定修复和本地验收，尚未部署，也不代表整个考勤计划完成。

## 根因及批准范围

第135批实际AdminPanel／SelfPanel诊断确认：父读取已因负责人变化或成员停用拒绝，独立请假／通知子页面仍保留旧资料，撤权前获准的迟到通知回复也可回填。原SQL仍正常拒绝新的越权请求；本批修复浏览器父子授权失效接线，不改数据库权限或业务记录。

- 两个原父客户端增加单调的 `authorizationEpoch`。只在当前代GET收到经JSON错误封装及HTTP状态验证的明确身份／权限拒绝后增加；旧代、超时或已卸载的请求不得触发。
- 冻结拒绝分类：`unauthorized` 为401；`attendance_access_denied`、`employee_password_authentication_required`、`enterprise_management_disabled`、`forbidden_origin` 为403。`attendance_disabled`、平台暂停、503、429和存储异常不归入这个分类。
- Admin独立区分GET拒绝，不能扩大原POST的首次明确失败清编号规则。保存已确认之后的当前列表GET同样按读取规则处理；不撤销已确认的保存。
- Admin仅重置请假Launcher；Self同时重置请假及通知Launcher。key包含企业、原身份和上述代次。重置会卸载旧组件、清除未保存草稿和私有显示，已有pause机制阻止迟到响应回填。
- 不以父blocked／ready、worker.active、canClock或moduleEnabled永久禁用子入口。有效成员即便不能打卡，也可能仍有权读取请假历史；用户显式重开后仍由子接口独立授权。
- 原持久化pending不删除、不改写、不新编操作号。关闭页面不等于撤销已发送操作；新子实例先GET原收据或通知原状态，只有原有确认流程能结清。

## 验收边界

复用第135批实际父组件、默认handler、当前111／122／125及现有隔离PG15。负责人变化、成员停用、撤权前已获准的通知延迟交付用于严格修复断言。再区分worker单独停用、普通打卡关闭、503和平台暂停；保持零浏览器业务POST，准备的原RPC申请／批准与数据库基线不变。

子客户端补新实例重开、在途POST暂停后的原pending字节保留和GET恢复单元测试；这与浏览器GET-only验收分开报告，不把纯测试说成实际手机写入验收。真实Auth／PostgREST／Next／完整企业壳及手机不在本轮运行范围。
