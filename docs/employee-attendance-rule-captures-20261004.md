# 三层候选来源留存：第149批契约与验收

日期：2026-10-04。承接[三层只读预览](employee-attendance-rule-preview-20261004.md)。本批新增独立来源留存后端，不改旧打卡、规则写入、审批、工时、周期锁定或真实数据。不开启生产开关，不部署。

## 保存的是什么

这是「服务器在本次保存时观察到的完整候选来源」，不是「过去实际采用的正式规则」。保存查询过去或未来日期的结果，都不能证明该日期的实际业务采用。

必须分清四件事：

| 内容 | 本批含义 |
| --- | --- |
| 原候选生效边界 | 127／129保存的日期、时区及UTC区间，不因留存而正式启用 |
| 本次观察时间 observedAt | 本次独立事务调用130读到来源的时间 |
| 原正文读取时间 sourceReadAt | 第一次保存该正文时其中的readAt；去重后可早于本次观察 |
| 留存操作时间 recordedAt | 新留存回执追加时间，不冒充历史可信时间戳 |

当前归组可追加结束／取消，组状态和人员资料也可变；因此不能只保存ID然后将来重新读取当前表作为旧依据。原补正周期锁只拦截对应补正路径，不冻结组、规则或整期工时。本批只把完整来源正文留存，尚未把来源ID绑定到正式计算、审批或封账版本。

现有来源解析器会使用当前运行环境的时区数据重新推导UTC。归档读取不得借当前Intl／tzdata重新计算并覆盖原边界，所以新协议保存并核验原文本字节，不把重新执行当前解析器称为历史重演。若以后要固定计算结果，仍需独立保存完整输入事实、解析结果及不可变算法版本，并按明确采用时点绑定。

## 独立接口与恢复

- 新接口 `/api/merchant-enterprise/attendance/rule-captures`，独立服务端开关 `FAOLLA_ATTENDANCE_RULE_CAPTURES_ENABLED=1`，默认关闭。没有页面、列表、自动保存、导出、轮询或新前端开关。
- GET只按商户、考勤档案、原操作编号读取一条回执；没有记录返回null。没有列表不等于可以全量读取，丢失原编号的可发现入口尚未交付。
- POST只接受查询、原编号、1–7个当地日期、理由及预期员工／登录双身份，不接受客户端提交来源、actor或模块状态。服务器重新授权后在同一事务调用130，完整读取后才追加新账本。
- 任一来源超限均拒绝保存完整凭据，不拼接分页，不把未知当作不存在。新保存要求当前双方身份启用和模块开放；原号恢复不受新保存的暂停或额度限制。
- 商户内原编号唯一。同actor、worker、双身份及完整命令的重试返回原回执，不再次读取130、不覆盖正文；不同命令冲突，跨actor／worker拒绝。
- GET和原号重试均重新检查当前负责人和双身份。首版原操作人必须仍是当前负责人；负责人转移后的归档交接另行设计，不绕过授权或自动重绑。停用可核对同身份旧凭据，换绑不能把旧来源套到新人。

## 存储与防积压

- 仅新增正文与小回执两张私有表，不给旧业务表增加外键或修改其写入行为。
- 正文保存130原始JSONB文本的实际UTF-8字节，含原始上下文；另外保存SHA-256和字节数。摘要是完整性校验，不是签名、数据库管理员防篡改证明或业务生效证明。
- 去重只排除变化的readAt，其他身份、日期、来源内容全部参与比较。摘要相同后仍比较实际来源内容，不能仅靠哈希认定同一来源。相同来源的新操作仅增加小回执，并保留原正文sourceReadAt和本次observedAt。
- 本地候选保护上限：单正文1MiB；每员工50份不同正文／8MiB；每商户500份不同正文／64MiB，以及1000条操作回执。它们是保守安全上限，尚非用户确认的商业套餐或真实容量结论。
- 配额在新商户级事务锁内原子核对，不自动删除、覆盖或清理历史凭据。已存在原号优先恢复。后续保留政策、档案移交和授权清理另做，不能因达到上限自动丢弃证据。
- 新表禁止原地更新、删除和清空，仅新服务角色RPC可调用；完整性依赖数据库权限、约束和运行流程，不宣称对特权管理员不可篡改。
