# 第134批：负责人待审请假工作台

状态：2026-10-04 用户在明确说明单工作区、视图切换和草稿影响后回复“继续”，同意按本范围实施；现已完成本地验收。冻结协议见[第134批契约](employee-attendance-leave-review-contract-20261004.md)，实测证据见[实施记录](employee-attendance-implementation-20260929.md)。不开生产、不迁移旧数据，不能据此视为真实试点或整体P1完成。

## 已确认缺口

- 原 `MerchantAttendanceLeavePanel.tsx` / `merchantAttendanceLeave.ts` 的负责人列表按提交时间倒序混列全部状态，没有待审批筛选。较早待审被后续已处理记录淹没，不是审批事务失效。
- 原 `merchantAttendanceOwnerBacklog.ts` 仅覆盖 correction / revision / missing，并要求声明结束时间不晚于提交时间；请假可以在未来，不能直接塞进旧三类契约而不改变其语义。
- 原 `AttendanceLeaveClient.detail()` 可以按已发现的申请编号读取详情，无须在原首页出现；但客户端须先 initialize 到 ready，且必须先处理已有 pending。批准／驳回依据最新详情的权限和 revision，仍走原API与原编号恢复。
- 原122具有 `(merchant_id,submitted_at desc,request_id desc)` 负责人索引及至多三条申请历史，可为新增只读发现接口提供有界候选扫描，不需要新建或重写业务表。
- 员工自己的排班查看已经存在，本轮不重复作为新功能实施；手动日历的员工可见范围仍是另一项待定规则。

## 已确认的实现范围

1. 在负责人请假入口提供“待审批 / 全部申请”，保持单一可写审批工作区，不并排挂载两套 `AttendanceLeaveClient`。新功能关闭时保持原入口；员工自己的请假入口不变。
2. 新增独立默认关闭的只读待审发现接口和精确DTO，不扩旧三类待审协议、不修改122或133包装、原审批权限和业务规则。
3. 复用既有索引，候选先有界扫描，再核验完整历史及当前 submitted 状态。返回扫描数和下一候选游标；空结果但尚有候选时明确允许继续查询。不能把候选上限称作完整待审总数、生产I/O上限或冻结快照，也不能后台不停翻页扫描全部历史。
4. 选择申请后重新调用原详情接口；列表只是发现线索，不授权审批。原有待确认操作始终优先恢复，不因切换视图／选中另一申请覆盖原编号或自动重发。
5. 批准／驳回及全部申请中的既有处理继续使用原客户端和服务器；133通知是否捕获仍由原通知开关决定。保持理由、明确确认、失败处理及无维护发布边界。

## 为什么需要先确认

这项工作需要调整已经可用的负责人请假页面及视图切换，而不只是新增只读按钮。切换时必须处理未提交理由／草稿和结果待确认状态。按照 `PROJECT_RULES.md`，影响既有成功UI路径前先解释并取得同意。

不推荐并排新增第二个独立审批Launcher：两个客户端会共享原pending槽。原存储核验和SQL revision能拒绝覆盖或重复决定，但一方完成恢复后，另一方仍可能显示结果待确认，需要重新核对；同槽不等于单工作区互斥。

## 确认后的验收终点

- 待审发现→最新详情→明确批准／驳回→原收据；已撤回／被其他会话处理的候选按最新状态拒绝重复处理。
- 未来请假、全部已处理的空候选页、跨页待审、当前负责人变化、跨商户、成员解绑历史与暂停读取。
- 已有pending先恢复、丢回复、视图切换的草稿提示、隐藏／卸载迟到回复、390px和原全部申请路径回归。
- 只合成数据、本地复用现有PG及内存浏览器harness；结束停服务，不建立新集群、不完整构建、不连接生产。

已先冻结确切协议与UI编排，再并行实现和验收；不扩大到待审邮件、自动审批或保留期删除。完成情况以实施记录为准，不将获准实施等同于已验收或获准上线。
