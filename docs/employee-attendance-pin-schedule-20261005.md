# 门店 PIN：明确选班与开班核准引用（本地限定交付）

2026-10-05，第170批。延续167获准的四通路兼容接入范围，本批完成门店 PIN 选班、实际核准引用及原号恢复的本地限定验收。当前候选143默认关闭，尚未部署或启用真实商户，没有访问生产账号、回填历史或修改工资；普通网页实际核准引用与四通路统一验收仍未完成。

## 员工路径与权限

现有门店 PIN 打卡页接入“本次排班与 PIN 上班”。员工输入本人工号和 PIN，经原设备、当前成员、角色和 PIN 凭据核验后，才读取本人在终端地点的候选；必须明确选择一个排班或“不关联排班”，不自动分配唯一候选。

候选读取、原号核对和确认上班都使用 POST，因为每次需要重新走原 begin、真实 KDF 与最终租约校验。不会按工号开放无凭据 GET，也不接受浏览器声明 `verified=true`。读取候选不产生考勤业务事实，但会计入原 PIN 认证尝试并消费所获得的短期租约，不能称为全库零写入。

配对设备不证明员工真实到场；需要定位核验的地点仍不能由 PIN 绕过。休息、结束休息和下班仍走原 PIN 接口。旧 PIN RPC 和134包装器的定义不变。

## 协议与保存事实

新接口为 [terminal-schedule](../src/app/api/merchant-enterprise/attendance/terminal-schedule/route-handler.ts)，只接受 `workerNo、pin、command、operationId、selection`。企业与终端来自原设备 cookie，不接受请求体提供员工权限、规则正文或负责人核准编号。请求体限8KiB、总读取期限5秒，同源和规范域名检查、禁缓存及错误去敏沿用独立处理器边界。

[143迁移](../scripts/supabase-migrations/202610050143_merchant_attendance_pin_schedule.sql) 新RPC `faolla_attendance_pin_schedule_v1` 保留112原八参数，追加 `p_selection、p_allow_schedule、p_bind_rules`。成功原始结果精确为：

`{protocol:'pin-schedule-v1',clock,choices,association,adoption}`

`clock` 保持原 PIN 的13字段；HTTP另附 `ok、moduleEnabled、selectionEnabled`。不会返回 PIN、salt、verifier、pepper、设备秘密或认证租约。

- 新上班保留原 `kiosk` 事件和107不可变 PIN 回执，同一业务子事务追加137明确关系与141共享的紧凑核准引用。
- `linked、unselected、unverified` 分别表示原选择可核对、明确不关联、原选择待核验；未核准、缺发布依据、已取消、地点变化和超出选择窗口不伪装成有效核准。
- `adopted` 固定140核准的操作编号、版本、来源编号、SHA-256及保存时间，不复制整份规则正文。无核准明确为 `not_approved`，不默认零宽限。
- 当前员工双身份由 PIN 校验后持锁的成员资料确定；其中 Auth ID 是成员绑定快照，不是声称 PIN 请求具有员工登录会话。
- 原133整班规则绑定仍由独立开关控制；启用时以 `('pin', null)` 调用原私有绑定器。它不被排班核准引用替代，也不会因启用选班而暗中开启。
- 候选只在无原号、无新命令的已验证状态读取列出，限终端／当前默认地点、当地前一天至后一天；101哨兵、最多100项、48KiB候选及64KiB总结果。受限时返回明确的受限空集合，不代表没有排班或缺勤。

## 租约与事务边界

新RPC沿112保留两层事务语义，而不是把旧RPC整体放进捕获异常的外层包装：

1. 原请求基础校验后，先调用106 `pin_finish`。当前设备与成员、角色、凭据修订及租约仍由原逻辑核对；租约消费位于业务子事务外。
2. 业务子事务保留112原身份、旧回执、序号、重新取服务器时间、租约期限、地点、在职期和状态转换校验；随后保存原事件／PIN回执、可选133绑定、明确关联与采用引用。
3. 已知业务拒绝以安全 `{error}` 结果返回：内层业务事实回滚，外层认证消费可提交。因此不得用同一认证租约重新尝试另一个业务操作。
4. 未知存储约束、基础设施等异常仍沿112外抛，整个事务可能连租约消费一同回滚。这里不承诺未知故障或数据库取消后仍能保留消费，也不把这类失败吞成正常拒绝。恢复仍须重新输入 PIN，重新核对原编号。

原 finish 保留商户／设置共享锁、成员与角色锁及人员排他锁直到提交；人员锁与140核准人员共享锁协调实际采用的核准版本。不模仿负责人调用140，不把 `recordedAt` 当作提交时刻证明。

## 原号恢复与页面隐私

原号读取使用 `command:null`，不自动重发。每次恢复仍需当前有效设备、当前本人 PIN 和成员权限；不同于扫码原号 GET，不能承诺撤销设备后 PIN 仍可恢复。

已有同号、同命令、同选择的成功记录恢复原关联及核准引用；改变选择返回冲突。旧成功记录没有新关系／侧证时只读显示缺失，不补写历史；新命令不能把旧回执冒充为本批已采证成功。排班后来取消另行显示当前取消状态，不重写原打卡或原引用。

新选班功能关闭时，所有带命令的新接口调用均拒绝，`command:null` 原号核对仍可在原基础通路有效且重新授权后进行。平台暂停的新上班门槛与112既有同号重放语义分开，不把开关回退解释为自动改送旧上班。

客户端只在本标签页会话中保留企业、设备、工号、原命令、编号及明确选择；不保存 PIN、租约、验证结果或候选名单。PIN仅短期内存保留用于一次明确确认，隐藏、离开、换人或到期清屏；不自动提交、不离线补传。旧／新待确认编号均未核清时阻止新动作；损坏记录不静默删除。公共终端在本次PIN验证成功前不展示原号或原选择细节，失败也不显示员工资料。页面取消请求不等于取消服务器已接收的操作。实际浏览器覆盖下文四组路径；隐藏／期限／同步回调重入另以客户端测试覆盖，不冒称真实设备实测。
