## 2. 推荐先做的完整包

推荐先补 **账号停用联动 → 负责人待办核验 → 同一身份明确恢复**，再单独处理正式离职日期／再入职、无账号人员及工牌。相比继续扩排班权限，这个包先解决现有入口之间的实际衔接问题；但不是宣称C04全生命周期一次完成。

### 停用

1. 保留企业紧急停用能力。不能因为尚未下班、待审数量多或考勤模块暂停，就要求先让员工保有权限完成业务。
2. 仅对明确启用新联动的考勤商户／已关联人员，在企业停用事务中保存暂停依据、worker／employee／Auth、原状态和真实操作者，并暂停该考勤人员。不创建虚假员工、不冒充负责人。
3. 对旧PIN及该员工作为受托人／被管理对象的考勤委托做持久失效处理；不得只依靠当前active暂时隐藏。重新启用membership后也不能自动恢复旧凭证／委托。
4. 未结束班次、原申请、真实打卡、审计和归档不删除、不补写clock_out、不自动批准／驳回，不自动改变 `starts_on/ends_on`。仅记录需要负责人核验的关系和状态。
5. 处置清单应按需分页读取，不在停用事务中扫描完整历史、加载所有正文或逐条跨网络撤销。未关联考勤档案或未启用联动的旧成功路径应保持兼容。

“保留紧急停用能力”是业务上不以未结考勤阻止撤权，并非承诺数据库或网络故障时请求也必然成功；事务失败仍必须明确未确认，并保留原操作编号核对。

### 负责人处置

1. 负责人进入实际员工／考勤页面即可发现暂停及未结事项，不依赖被停用员工能够登录。
2. 分开显示：原始未结束工作／休息、待审申请、未知操作回执、当前凭证／委托状态。仅展示当前负责人有权看的内容，不将“没有读到”显示成“没有问题”。
3. 已有安全驳回、历史读取等能力可在真实身份和原规则允许时继续使用；不能为收尾绕过原身份检查、伪造员工提交或自动恢复员工账号。
4. 真正离职且不会回来的员工，其未闭班次如何留痕处置仍是后续独立业务；本包不虚构管理员代打卡能力，也不把“已标记待处理”算作班次已结束。

### 明确恢复

1. 企业账号重新active不会自动启用考勤。负责人需核对同一worker、employee与Auth，再明确恢复；任何换人、换绑或归属不明继续拒绝。
2. 新恢复入口不能机械调用064：它目前在开放班次时禁止active变化。须新增严格的同身份恢复路径，恢复的是原始状态供本人按原通路实际收尾，而不是生成或回填一条下班事件。
3. 原本就未启用的人员不借恢复动作自动开通；当前角色、地点、任职区间、平台资格仍按原规则核验，不自动添加角色权限。
4. 旧PIN不得复活，需另行设置；旧审批委托不得复活，需负责人重新授予。已有最小操作回执仍按原Auth读回，不因失效而改写历史证明。
5. 明确区分“账号恢复”“考勤恢复”“设置PIN”“重新授予委托”四个结果。没有对应确认回执不能显示为完成。

## 3. 必须一起处理的技术接点

- 企业员工update的现有RPC／任务交接／审计／版本与原号重放边界，不能先停账号、后发第二个请求补考勤暂停。先前已成功旧号不得重放时补写新的暂停事实。
- 锁序必须从外层统一设计。现011已先持employee UPDATE；155等考勤操作采用settings→worker→employee。不能在employee触发器中再反向获取settings锁，也不能只靠浏览器预检避免并发。
- 旧064启用路径须识别尚未解除的新暂停，不允许普通编辑绕过新恢复。旧单任职期约束不顺带放宽。
- PIN设置／撤销及消费中租约、漏卡160与申请162的可用性、发新委托、原号恢复要共同核对暂停／失效依据。仅改UI或worker.active不能完成安全边界。
- 可以采用独立追加的失效代际／依据，避免扫描全部历史授权；若采用此设计，须有精确的凭证／授权绑定证明，不能只靠时间戳先后猜测。旧历史回执按当时保存证明解释，不按当前委托是否有效重新否定。
- 新功能默认关闭、先本地验收；已有暂停记录的保护与安全恢复不应因回退开关而被绕过。未触发新功能的旧数据不回填、不迁移。

本节是需确认后的设计约束，不预先承诺只改固定几个函数即可完成；实现前还需冻结实际API／SQL契约。只追加新迁移，不改已存在迁移文件。
