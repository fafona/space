# 第194批：账号状态原号的独立读取

状态：本地实现与限定验收完成，未部署。承接193的明确遗留项与用户“继续”。实际结果与限制见[交付记录](employee-attendance-account-status-recovery-20261006.md)。

## 原因与范围

193的账号状态操作已经保存真实 Auth、原号、目标员工及指纹；失去 employees.view 后，原员工管理页不能再承担待确认结果读取。164 SQL 的 recover-status 本来允许仍绑定原 Auth 的操作者读取自己的最小历史回执，但独立恢复页此前只识别两类审批委托 pending。

本批仅把第三类 account-status 接入已有 `/enterprise/attendance-recovery`。不新增恢复写入权限、不重发 PATCH、不修改原 SQL、账号状态写入、审批委托解析器或真实业务数据。

## 固定行为

- 页面仍验证当前员工 Supabase session 与 getUser；身份变化即时隐藏并中断。沿用原认证政策，不宣称端点强制 password-only。
- 用户先显式扫描当前标签页 sessionStorage，再选一个原编号读取；扫描不发考勤请求。三个 family 合计最多64项、存储最多2048个 key。
- account-status pending 必须符合193的精确5字段结构、8KiB限制、真实 Auth、精确 key、合法命令及 SHA 指纹；不暴露目标员工、交接意图或命令正文。
- 复用原状态客户端，但适配器只接受 recover-status GET，禁止 setItem。仅身份、原字节与完整回执仍匹配时删除该一个 pending key。
- 查无回执、503、身份失效、换绑、错误指纹、存储变化或隐藏均不能视为失败，也不重发／清空原编号。
- 回执为历史记录，不证明当前账号状态。恢复账号、解除考勤暂停、新 PIN、重新委托是四件不同的事；本页一件也不执行。
- 旧两类委托保留原 helper/client，统一选择方式仅增加第三种明确标签。

## 验收边界

使用原停止的PG15隔离环境与一次性owned schema；只合成身份，不建立新集群／数据库副本，不做完整构建或连接生产。真实Manager失响应产生pending，再真实提交撤角色权限，独立Selector和RecoveryPage读取原号；认证SDK与membership初始化为明确合成夹具，HTTP处理器、服务与SQL为实际代码。

成员停用／身份换绑另做真实SQL事务回滚验证，不把它冒称为真实手机、真实登录或生产端到端证据。浏览器仅内存打包，所有资源finally关闭并验证本地基线恢复。

## 保留限制

必须仍能登录原 Auth，并保留原标签页的本地编号。另一个浏览器、清空站点数据、丢失标签页或已换绑身份，不能自动找回全部操作；需交负责人核验。本批不实现全局账号找回，也不放宽任何角色权限。
