# 第209批：整段请假及封存拒绝的实际页面闭环

2026-10-07，承接[208页面与并发验收](employee-attendance-posthoc-interaction-concurrency-20261006.md)，继续203已批准范围。本批补齐整段请假“不适用”和正式异常封存拒绝的实际父页面流程，并修复一个真实接口错误映射缺口。**仅本地合成验收，未部署，没有真实账号、手机或员工数据操作。**

## 根因与产品修复

SQL174已经拒绝在封存周期内保存新的正式处理，抛出`attendance_period_sealed`；但是[异常接口错误表](../src/lib/merchantAttendancePlanExceptions.ts)没有列出该码。真实服务因此将它降为`attendance_unavailable`，路由返回503，而不是准确的409。此前原生SQL拒绝通过，不能证明HTTP接口和页面提示也正确。

本批产品改动仅两处：

- 在错误表补充精确`attendance_period_sealed:409`。数据库错误附带私密详情、未知错误等仍走原脱敏失败路径，不把任意文本当成可信业务错误。
- [异常客户端](../src/lib/merchantAttendancePlanExceptionClient.ts)只在收到严格匹配的409错误信封后提示周期已封存，先核对原编号；需要继续处理时，由负责人按原流程重开周期。原待确认字节保留，不自动重发、清号或撤销操作。

没有修改SQL封存规则、审批结果、原成功路径、权限、自动重试或明确结束尝试的条件。封存状态未加入出勤来源指纹；页面尚未提前获取并禁用所有封存操作按钮，本批验证的是提交被准确、安全拒绝后的真实处理流程。

## 七组新增实际页面验收

[新浏览器验收器](../scripts/fixtures/attendance-plan-posthoc-full-leave-browser.mjs)复用208回环桥和真实AdminPanel／SelfPanel，走实际HTTP处理器、服务及拥有的合成SQL。独立新建无头Chromium上下文，不接管用户已有浏览器；390px是布局验收，不是手机实机。

1. 实际已批准整段请假、明确空来源采用后，负责人当前依据为`not_applicable`。新写默认关闭；明确开启并重新读取后，只允许“不适用”或继续核查，不能选择确认异常、豁免或两项未触发结案。理由必填，取消确认不发送POST。
2. 通过真实页面明确保存“不适用”，服务器提交后截断成功响应，保留精确原编号。随后通过真实周期服务执行送审、本人确认、负责人封存；没有直接改sealed投影，也没有伪造浏览器决定。
3. 关闭新采用／v3决定写开关后，页面只读核对原编号，仍取回封存前已成功的原回执并清除对应待确认键；不重复保存，不冒充已经重新核验当前依据。
4. 再次明确读取后尝试新处理，实际HTTP返回`409 attendance_period_sealed`，页面显示封存原因并清除旧详情，保留新的待确认原号。整库事实哈希和归档保持不变。
5. 明确GET原号未找到回执时保留编号、不自动POST；用户明确重试先GET再以同编号、同正文POST，仍正确拒绝且零写入。明确“结束本次尝试”再GET、核验双身份后才清除本地待确认状态，不改数据库决定。
6. 本人实际父页显示保存时“不适用”，保持`current=null`及`not_checked`，不把历史结论当成当前事实。独立消息类型正确；明确消息标读后，业务决定仍未已读，周期归档不变。
7. 负责人按已知成功原编号再次只读查询，封存后仍取得原“不适用”回执，没有新POST。旧155归档及本次首次封存的归档原文／SHA均保持。

新增页面共25次业务请求：21 GET、4 POST。4次POST为一次成功决定、两次同编号封存拒绝和一次独立消息标读；只有2次成功写入，不把拒绝计为新记录。所有GET无写入，两次拒绝也在桥的原串行SQL执行区比较完整事实哈希，验证`rejectedPostFactHashUnchanged=true`。

周期封存使用实际服务及SQL，但并非在浏览器周期页面逐按钮执行。请假申请／批准和空来源采用也由原207夹具通过真实写入器准备；本批真实浏览器从正式异常父页开始，不冒称全流程每一步都由手机操作。
