# Faolla 无维护发布与中断恢复流程

本流程适用于已有应用构建的预约发布和发布工具维护。正式站在候选验证期间继续提供服务；邮件保持关闭。发布成功必须同时满足实际路由、数据库代次、后台任务所有权、版本记录和收尾证据一致，不能仅凭进程在线或 CI 绿色判断。

## 发布前先判断当前状态

先独立读取数据库、实际 Nginx 配置、公开版本、PM2 进程身份、后台任务门禁、活动版本元数据和上次操作证据。多次读取期间有变化时，重新进行只读检查，不复用混合时点的结果。

| 当前状态 | 后续路径 | 禁止操作 |
| --- | --- | --- |
| 数据库未激活，旧版本和旧任务完整，且没有未结束操作 | 使用全新资格验证和正式准入 | 复用过期备份、租约或失败候选 |
| 控制器或看门狗仍拥有操作 | 观察原操作 | 并发发布、夺取锁、重复提交 |
| 数据库激活，实际路由在兼容回退版本，收尾未完成 | 独立核对现场，再审查活动代次的收尾与续接 | 重放激活 SQL、重复重启已暂停旧任务、清空操作目录 |
| 数据库激活，实际路由在主版本，证据未闭合 | 验证实际后置条件并审查收尾 | 用手写成功文件代替验证 |
| 实际路由、数据库或任务所有权冲突 | 停止变更并保留证据 | 直接按活动版本 JSON 推断实际流量 |
| 主版本、元数据、证书、日记、工作门禁及操作收尾全部验证一致 | 发布完成，进入观察 | 把邮件配置缺失误当作已启用邮件 |

状态分类实现在 `scripts/release-toolchain-publication-state.mjs`。分类结果不提供生产操作权限。

## 正常发布顺序

1. 确定应用提交、两份构建、依赖和迁移的身份，分别绑定应用版本与工具版本。工具变更不得给旧构建重新贴上新的应用版本。
2. 验证精确提交的 PR 和正式提交 CI、工具完整检出与源文件指纹。清单缺失或版本漂移必须在安装或启动前拒绝。
3. 核对内存、磁盘、端口、数据库容器及系统标识、现有进程和备份空间。需要构建时保留原有 6 GiB 可用内存门槛；已构建的续接不得重复消耗构建资源。
4. 在全新隔离数据库验证兼容性、备份恢复、正常切换和控制器中断。隔离数据库不得访问正式网络，不能把正式 PID 或租约伪装成测试身份。
5. 在正式全局锁内生成新的加密备份，验证其确为正式库，并重新核对应用、数据库和兼容性。只保存备份成功日志而不验证备份来源，不算通过。
6. 检查主候选和兼容回退版本的实际进程、环境、监听端口、源码和构建，并取得新的就绪证据。不得修改旧证据时间来延长有效期。
7. 建立一次性操作窗口和独立看门狗。看门狗继承真实内核锁；SSH 或控制器退出不能释放并发保护。
8. 安装窄范围预约入口围栏，确认新请求被拒绝、无关功能仍可用，并排空旧请求。
9. 仅在未激活路径执行已批准的数据库事务，然后确认其提交结果。活动代次路径不得再次调用激活事务。
10. 旧预约任务最多执行一次身份绑定的暂停重启；只读确认实际环境和任务所有权。确认结果未知时不自动再发一次 RPC。
11. 切换实际路由，验证公开版本、登录与权限烟测及关键预约路径，再同步活动版本记录与 PM2 持久配置。
12. 完成版本保留证书后才允许打开对应代次的预约工作门禁。完成日记与操作收尾，再做一次独立只读复核。

现有固定入口是 `scripts/release-toolchain-release.mjs`。其中 `status` 是只读诊断，`validate` 会创建备份和准入证据，但不切流量；`qualify` 会创建并停止隔离资源。`archive-recovered` 只适用于其代码中明确绑定并经批准的历史操作，不是通用清锁命令。存在未结束操作或数据库已激活时，不直接执行旧 `publish`。

## 失败后的判断和恢复

所有有副作用的步骤先持久记录意图，再执行一次，并独立确认结果。超时、连接中断和丢失确认不代表副作用没有发生。

数据库提交结果不明时，恢复程序通过事务锁屏障等待提交或回滚，再确定目标。只有证明数据库未激活、原记录未被已提交事务修改且原旧任务完整，才可回到旧基线；否则只能使用已验证的兼容回退版本。

恢复按以下顺序收尾：确认真实租约和控制器已退出、捕获现场、数据库屏障、关闭预约工作门禁、必要时核对原有单次暂停结果、恢复兼容路由、解除临时围栏、验证公开版本、更新版本元数据、持久进程配置、写入恢复完成凭证。恢复完成不能标为正常发布完成。

每个恢复步骤分别写入开始证据。子进程退出时保留退出码、信号、错误分类、输出长度和哈希，以及允许范围内的源文件行号；不记录密码、原始环境或任意异常文本。诊断写入失败也不能掩盖原始失败或触发重复变更。

公开探测每个请求最多 5 秒，总预算不超过 30 秒，校验 HTTP 200、`ok` 和精确构建版本。请求头成功但响应体卡住、重定向、错误版本和过大响应体都不能算成功。仅只读探测可在预算内有限重试。

## PM2 和 Next 的真实验收

固定环境为 Node 20.20.1、PM2 6.0.14、Next 16.3.4。Next 收到 SIGINT 后正常清理会以 130 退出，不能一概按退出 0 建模。

新增验证路径要求同时证明：一次身份绑定的重启、PM2 原始日志在锚定偏移后新增唯一的目标 SIGINT 终止记录、同一守护进程、正确旧新 PID、完整环境仅发生允许变化、重启计数恰好增加一次、其他进程及其实际环境未变。只有一个数值 130 或人工构造 JSON，不足以授权发布。原有退出 0 的规则保持不变。

CI 的真实 PM2 验收使用单独的私有 HOME、真实 Next 构建和共享的生产 RPC 传输。它明确拒绝存在正式 PM2 或活动版本锚点的主机。安装只发生在一次性 CI 环境；正式主机不能设置 CI 标志后借此运行测试。

## 验收范围和完成标准

| 验收层 | 必须验证的内容 | 不能替代的验收 |
| --- | --- | --- |
| 契约和故障注入测试 | 指纹、顺序、过期、越权、重复执行拒绝、每个恢复步骤的失败诊断 | 真实进程和真实网络 |
| Nginx 和隔离 PostgreSQL 演练 | 正常切换、提交前后控制器退出、事务屏障、回退、备份恢复、清理 | PM2 实际重启与生产固定适配器 |
| 真实 PM2 和 Next 验收 | 实际 SIGINT、130、原始环境、单次 RPC、旧请求拒绝、无关进程保持 | 数据库激活和整个生产收尾 |
| 生产固定适配器验收 | 路径、进程、数据库、持久配置、证书、工作门禁全部一致 | 用若干独立组件通过来宣称全链路通过 |
| 发布后只读复核 | 两个公网入口、权限烟测、数据库代次、进程差异、日记、证书、锁和门禁闭合 | 仅有首页 200 或进程 online |

每次结论标明精确提交、验收层、通过项和未通过项。失败运行、候选、备份和日志全部保留，不覆盖后重试。

## 活动数据库代次的续接要求

2026 年 10 月 28 日的中断属于“数据库已激活、兼容回退在线、收尾未完成”，不能进入未激活发布路径。新的续接必须独立验证当前代次、已批准事务结果、实际路由、已暂停旧任务、关闭的预约工作门禁、不可变构建和完整失败证据。

应先在隔离环境验证同样的活动代次状态，再取得新的备份、兼容回退就绪证据、精确工具 CI 和一次性准入。旧租约已经过期，不能重新使用；旧失败日记只能保留并通过新日记关联，不能改写成成功。对受保护元数据及旧操作状态的收尾，应明确列出将写入的文件、比较条件、审计保留方式和失败边界后取得授权。

在生产适配器和该续接路径完成验收前，不能把发布工具链称为已全部跑通。

## 已完成保存、但收尾失败的固定续接

2026-10-29 的 `9ab3cc54` 尝试已经校正活动元数据并完成一次 PM2 保存，随后在后置身份复核拒绝。不得再次运行该次 reconcile，也不得通过新 UUID、删除失败标记、重复 save 或重放激活事务重新开始。

新的 `release-toolchain-post-save-entry.mjs` 只接受 `qualify` 和 `close`。安装使用独立的 `release-toolchain-post-save-install.mjs`，要求当前精确 main 的两轮完整 CI、旧工具完整指纹、固定失败目录的全部文件字节与 inode、当前真实 PM2 peer/进程集/保存结果和公网兼容版本一致。旧工具与失败目录不改动。任何未知的新尝试都会拒绝自动续接。

新窗口仅生成明确标注“只读复核、没有重新写入/保存”的凭证，在同级新私有目录保存；新备份、隔离验收及原有内核锁检查仍完整执行。只有全部后置条件和封印再次复核成功，才把原操作目录原 inode 归档，并释放本次实际拥有的替代目录。独立 reader 确认收尾后，才进入原有正常发布入口。

长时间比较 PM2 守护进程时，`/proc/<pid>` 目录 inode 和时间戳不作为进程出生身份；PID、启动 ticks、PPID、UID、命令摘要、cwd/executable 身份、boot ID、真实 socket peer 和完整进程集仍逐项验证。原始单次采集的漂移保护及共享 PM2 适配器不放宽。

CI 另用实际私有 PM2、Next 和活动隔离 PostgreSQL 验证“保存有完整完成凭证、后置失败”的只读续接，以及“保存后缺少完成凭证”的拒绝。该演练只使用真实自有资源，不能把 JSON 转为正式权限；旧失败证据全部保留。正式上线成功前，本节只是已实现/待验收的操作约束，不是成功发布声明。
