# 第210批：故障备用登记、恢复核对与结案边界

2026-10-07，承接[209限定交互验收](employee-attendance-posthoc-full-leave-sealed-20261007.md)，返回固定清单C24的实际业务缺口。本批为源码调查与方案定界，**未实施新的业务规则、未启动数据库或浏览器、未访问生产、未部署**。以下建议涉及新的结案条件和周期检查，待用户明确确认；不把此前203的事后采用批准扩大为这一新规则的批准。

## 1. 实际缺口

[原计划第16节](employee-attendance-plan-20260929.md)要求“门店临时登记→恢复后受控补正→双方核对”，不把网页离线声明当成已完成可信打卡。

已有普通网页、定位、现场码、PIN及各申请的原号恢复；独立[恢复页](../src/app/enterprise/attendance-recovery/page.tsx)用于已支持的特定待确认操作。它不是故障登记台账，也不自动覆盖所有补正／漏卡pending。当前欠缺的是可追溯的故障事件、逐人声明、实际处理引用、双方核对及结案，不是再加一个查询原编号页面。

## 2. 复用已有处理，不增加另一套计时数据

| 真实情况 | 复用已有处理 | 新登记可保存的关联 |
| --- | --- | --- |
| 原始打卡已成功，只是响应丢失 | 原通道核对原操作 | 真实原操作及事件引用，不再申请同一时段 |
| 已有班次，但需核定时间 | 原补正申请及实际096审批 | startEvent、request、明确批准operation／effect版本 |
| 已批准补正又需调整 | 原095连续修订 | 原班次及当前有效effect的明确版本 |
| 整段确无打卡，满足既有条件 | 原103漏卡申请／修订／审批 | root、request及当前批准operation |
| 已有漏卡由合法委托人审批 | 原160权限及审批依据 | 原决定及真实审批者，不改成负责人身份 |

依据：[补正协议](../src/lib/merchantAttendanceCorrection.ts)、[补正服务](../src/lib/merchantAttendanceCorrection.server.ts)、[当前审批服务](../src/lib/merchantAttendanceCurrentCorrectionDecision.server.ts)、[漏卡协议](../src/lib/merchantAttendanceMissing.ts)、[103有效漏卡及补正检查](../scripts/supabase-migrations/202610010103_merchant_attendance_missing_revisions.sql)。

新故障记录不写原始events，不写correction effects，不自行创建或批准missing。既有统一报表仍只从原始／有效核定／有效漏卡取工时，故障申报的时间不能再加一次。

推荐首版采用**先通过原流程保存申请，再单独明确关联**。关联失败时显示“原申请已保存、尚未关联”，用故障流程自己的操作号核对；不撤销原成功申请、不自动重复提交。旧补正与漏卡命令都是严格字段协议，不能随手增加incidentId。若以后要“一次按钮原子创建申请并关联”，需要新包装器及另行批准其失败回滚会影响原成功路径的语义。

## 3. 建议的完整工作包（待确认）

### 事件与逐人声明

- 负责人登记故障类型、受影响入口／地点、申报时段和说明，故障结束与个别员工恢复完成分开处理。
- 员工提交自己的声明；负责人可依据纸表代录，但明确显示实际登记人和“负责人代录”，不能伪装成本人提交。
- 固定商户、worker、employee与Auth身份；申报时段、时区／明确UTC偏移、服务器接收时间分开保存。模糊或不存在的本地时间必须明确选择，不能猜测DST偏移。
- 记录当时已知的原操作编号和通道、纸表参考编号／说明；不收集PIN、密码、验证码、持续定位或不必要的敏感材料。首版不做OCR、附件仓库或无人审批的批量导入。
- 提供可提前打印的空白备用登记表。完全停机时靠事先保存的表记录，恢复后再录入；不承诺服务器宕机时仍能打开未缓存网页。

### 恢复核对与关联

先核对未知原操作，再选择实际原始事件或合法补正／漏卡结果。来源只能由服务端在当前授权及事务锁下核验，不能接受浏览器提供的“已批准”文字或任意requestId作为成功证明。

待审批、驳回、撤回、来源变化与确已解决应分别显示。可以记录处理进展，但只有合法完整依据及所需双方核对都满足，才可标为已核对结案。原关联快照、操作者和版本保留；后来来源修订时显示“依据已变化、需再核对”，不把旧关联悄悄解释成新批准。

同一逐人问题重复登记或被多事件引用时，必须有显式的重复归并／引用处理和审计，不能以静默覆盖消除，也不能据此重复计时。细分来源有界查询，超过范围明确要求缩小，不截断后冒称全部核完。

### 双方核对与结案

负责人提出有理由的恢复结果，员工对**该精确结果版本**明确确认或提出异议；已有消息“已读”不代替确认，负责人不能替员工点确认。确认只表示核对这份恢复记录，不等于工资确认或放弃争议。

有未排除的未知原号、待审申请、来源变化、身份不明或员工异议时保持未解决。员工被停用、换绑或不能合法确认时，不自动恢复账号、PIN或委托，不假造确认，也不强制结案；需要无账号／离职人员的人工证明替代流程时应另行明确，不能隐藏地加入首版。

## 4. 与周期的关键政策建议（待确认）

现有[150封存守卫](../scripts/supabase-migrations/202610050150_merchant_attendance_period_seal_guards.sql)只覆盖已有六类补正／漏卡表。新故障表不会自动进入守卫或周期来源；简单增加登记页，会让“仍有未核完故障”完全不影响现有封存。

建议这一包同时接入相关员工、相关时段的周期检查：

1. 未核完／有异议／关联依据变化的有效故障登记，阻止该范围的新送审、重新送审和封存；无关员工、日期或纯故障事件头不全局阻断。
2. 新版周期来源清单纳入已核对结果及其依据版本，同时兼容旧版本读取；员工确认绑定这份明确版本。登记或依据在确认后变化时，旧确认不能直接用于新封存。
3. 已有封存原文、SHA和历史确认不改。后来补报故障只使当前核对显示需要处理，不自动解封；需要变更工时仍须按原流程明确重开。
4. 无此类登记的旧路径保持原行为。关闭新登记写开关后，已有故障资料仍必须兼容读取，不能靠关开关忽略已有阻断。
5. 通过新向前兼容迁移及读取协议实现；不编辑旧迁移、不重算旧归档、不修改正常打卡／安全收尾行为。

这是**现有周期成功条件的有意变化**，须确认后实施。另一种选择是首版仅独立跟踪、不阻止周期封存；其影响必须明确展示，不能称已经具备完整周期防漏核对。推荐采用前述相关范围阻断方案。

## 5. 不能绕过的现有限制

- **未知原号不等于失败。** GET查无、超时或资料归属不明，不能直接转成“未打卡”。原通道有些需要真实PIN等重新认证；新页面不能以负责人查看故障记录为由绕过它。恢复点丢失资料时，更不能断言原操作从未成功。
- **开放班次不能用整段漏卡代替。** 当前补正批准要求原basis一致且原事件尾已结束；103漏卡也检查原始前态、事件、核定及其他有效／待审漏卡冲突。需要原允许通道真实收尾后重新核对；不得补写过去原始打卡。无法合法收尾的保持待处理。
- **故障不自动豁免申请期限、地点、任职或规则。** 超期和封存仍走原处理规则，不因为登记了故障就扩大窗口或代替审批。
- **旧身份限制不能顺手统一。** 某些历史补正允许inactive worker但仍要求有效成员与权限；漏卡新申请要求当前worker／地点active。新入口保留各来源真实权限，不把它们改成统一的宽松或一律禁止。
- **声明与已有封存事实区分。** 可以保留后来声明及异议，但不能把声明视为更改旧时段的授权。撤回／驳回等原本允许的行政动作也不因新增台账被全部禁止。

## 6. 恢复与灾备不是同一件事

[应用快照范围](../src/lib/platformAdminDataBackupScope.ts)明确不是完整数据库、Auth或独立异地备份。[现有数据库内容校验清单](../scripts/database-recovery-content-contract.mjs)目前覆盖pages、兑换操作／结算、迁移和快照恢复收据，没有考勤关系。这只能说明**现有验收证据不覆盖考勤**，不能据此断言真实全库备份没有包含考勤表。

本包业务恢复登记不等于真实灾备验收。之后须独立核对原始事件、核定／漏卡当前头、周期原文／SHA、身份与暂停代次、设备及PIN撤销、委托授予／撤销和故障台账的一致恢复；恢复点之后的未知操作必须继续核查。真实备份、PITR、隔离副本恢复及回切另需明确来源、权限、资源和目标，不在本次调查中启动，也不为每轮测试复制整库。

## 7. 确认后的实现及验收终点

按同一个完整工作包推进，不把多个孤立只读页算完成：独立追加账本和原号恢复→负责人／本人实际入口→明确来源关联及双方核对→获准的周期兼容检查→实际页面、并发和归档保护联合验收。

- 全流程绑定真实操作者与双身份，撤权／换绑／暂停后不泄露正文或恢复旧权限。
- 双击、丢响应、同号不同正文、原申请成功但关联失败、来源审批／修订与结案竞争、周期封存与新登记竞争，均有确定的幂等／CAS和零残留写入断言。
- 旧申请、原号恢复、无故障周期和固定版本导出保持兼容；本人异议不被已读吞掉，显示历史不代表当前资料仍有效。
- 25条等有界分页、正文／引用限额、超限拒绝、原号仍可读与窄屏交互一起验，不加高频轮询或复制完整依据到浏览器存储。
- 复用唯一已有合成本地环境，不开生产功能，不创建真实商户／员工，不复制依赖或完整构建；验收后恢复基线、停止进程。
