## 推荐判定口径

1. 以原发布计划的保存UTC起止及开班时固定核准为准，不用现在的通用／组／个人规则重算历史。缺失、停用、0分钟和未配置分别处理；不同固定核准版本不能挑最高版本混算。
2. 新流程选用最新批准核定时间，没有补正时沿用原始时间，同时显示原始对照。不修改原事实、原核定、原报表或原导出。
3. 对同计划多段完整且已核实的记录，用未经计划裁剪的首／末有效端点各判断一次，不能每一段重复算迟到。跨班／归属含糊、互相重叠、完全移出计划、零时长、未结束或边界休息影响判断时先待核查，不挑选“看起来正常”的一段。
4. 建议差值严格大于已核准宽限才触发；恰好相等不触发，0分钟不是关闭。保存微秒，展示同时区分原始差值、宽限和超出宽限量，避免用一个“异常分钟数”暗含扣除／舍入规则。
5. 首版正式确认应在计划结束且影响判断的记录已结束之后；进行中只显示进度／待核查，不将还没发生的下班判为早退。没有关联记录不能判缺勤；“未触发这两项”不等于整班正常或完整出勤。
6. 推荐首版任何可能影响边界的请假／漏卡／未关联或跨班资料先阻止自动形成结论，负责人核实处理；申请中不当豁免，拒绝／撤回／取消不当有效请假，整班假不显示正常出勤。人工理由不能越过身份、完整性、坏来源、超限等硬性校验。
7. 若用户选择请假自动抵扣，须另落实：只用当前approved且原双身份匹配的半开区间；连续覆盖计划起点／终点的并集调整相应边界，内部请假不平移两端、整段覆盖为不适用，请假与实际工作重叠单列冲突。日历优先级及独立漏卡明确认领仍不能由此推定。

## 最小真实闭环

### A. 服务端完整依据和候选

- 同一授权事务取得完整关联、固定核准源、最新补正、相关未关联记录及私有请假／日历／漏卡版本；不能在浏览器拼接数次独立HTTP结果冒充一致来源。
- 保留 merchant→settings→worker→employee 原锁序；沿用有界时间、1MiB、10关联段／2002原事件等上限。新的相关资料集合也必须哨兵检测超限，不偷偷取前N条后声称完整。
- 对当前绑定和原双身份逐项验证；不靠相同姓名、相同workerId或仅当前Auth推定历史归属。
- 负责人手动核对遗漏不替代服务器应能验证的完整性；影响边界的未关联记录要有可追溯解决路径，无法解决保持待核查。缺勤和无记录的处罚不属于本包。

### B. 追加式处理记录与原号恢复

- 只增加正式异常case／版本／处理记录，不复制现有申请／打卡账本。保存紧凑原编号、实际采用端点、核准引用、算法／政策版本、内容指纹、理由和处理人。
- 浏览器提交选择／理由／expectedRevision／expectedFingerprint及稳定operationId，不能提交可信规则值、计算结果或“complete=true”绕过服务端重读。
- 同一事务重新授权、重读源并做版本／内容比较；并发处理仅一个新版本成功。原号重放只恢复原收据，不追加第二个结果；来源变化要求重新预览。
- 后补正、请假后来批准／取消、新相关记录或计划取消不会改写旧确认。读取／提交时重验并标“来源变化，需复核”，通过新操作形成新版。只在读取／操作时重验就不能宣称实时后台失效通知。
- 已核查异常、说明后不认定异常、继续待核查须分别保存，理由不能抹掉证据；有员工异议时保留异议历史。已读不是同意，沉默不是确认。
- 申请事实错误时进入已有补正／连续修订／请假／漏卡流程；异常处理不能替代批准补正。来源新决定落定后再明确复核。

### C. 原工作区接线、本人结果和验收

- 复用现有核查详情的行动位置；异常操作在现有企业考勤工作区进入，不另外添加一组重复只读子页。主管委托未实现时仍限定负责人，不偷偷扩大现有角色。
- 当前SourcesPanel改日期会invalidate、关闭会卸载。新增表单／写请求前必须明确父级未保存及待确认离开协调；源／身份／企业／apiFetch改变、隐藏、过期响应都不能把旧结果显示到新员工。
- 待处理列表要能进入对应实际处理，不只显示数量；已批准记录进入连续修订，不重复首次申请。
- 新异常结果通知按原接收员工和Auth、结果版本去重，同事务记录通知引用；不往125请假FK硬塞新类型。明确已读，换绑不移交通知，不承诺邮件／推送或后台实时送达。
- 验收必须覆盖真实本地页面→处理器→服务→SQL的预览／处理／原号恢复／本人读取，及来源变化、并发、双身份、暂停、窄屏、恢复失败、通知去重。复用现有合成PG／回环，不复制数据库／依赖或完整构建。

“A有了候选”不是异常闭环完成；须A–C完整交付才报告这个限定工作包完成。C15仍须明确首版范围，整体P1、工资、全地区规则与设备支持不由本包自动完成。
