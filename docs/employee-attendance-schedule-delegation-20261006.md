# 第198批：主管排班委托，本地实施与验收

范围来自第197批[旧路径调查与确认边界](employee-attendance-schedule-delegation-boundary-20261006.md)，用户随后“继续”批准实施。协议见[冻结契约](employee-attendance-schedule-delegation-contract-20261006.md)。本批不部署、不接生产或真实员工数据，不新建数据库副本、不完整构建、不进入维护。

## 已实现

- 独立 `attendance.schedule.publish`／`attendance.schedule.cancel` 权限，依赖企业入口和本人考勤查看；不自动赋给旧角色，不包含规则核准、模板、全企业考勤或配置管理。
- 负责人明确选择主管、目标员工、地点、有效期与动作；管理自己被拒。授权前已存在的未来班次默认不纳入，需另外确认。
- 主管独立读取授权范围，预览明确的当地时间及 UTC 时间段后发布，或明确取消尚未开始的班次。每次最多32段，读取最多31个日历日；重复／不存在当地时间按原 DST 解析器明确处理，不按24小时推算日历日。
- 新167迁移三张私有追加表：授权、撤销、授权操作依据。真实主管 Auth 写入原排班账本，与授权依据及136发布身份依据同事务，不冒充 owner、不回填历史。
- 前向兼容136、137、120、128的五个判断点所属四个旧函数：旧 owner 路径保持，主管来源必须具有完整保存依据。历史读取不依赖当前授权仍有效；撤权不自动取消已有班次。
- 164暂停采集增加新授权双方，包括没有自身考勤档案的主管；关闭新功能开关时停用仍推进代次。账号重新启用不复活旧授权；不修改旧两类授权代次表。
- 在实际 Admin／Self 父页面增加独立入口、草稿离开保护；不阻止普通打卡，不把原 owner 配置或模板目录开放给主管。
- 第五类独立原号恢复：只核对本标签页、当前真实 Auth 的已保存意图。未知结果只 GET、不重 POST；匹配回执才精确解除原标记。撤去当前权限不等于删除原回执，换绑则不能读取原员工意图。

## 安全与兼容

- 普通新操作受服务端精确开关和商户白名单限制，默认关闭。负责人关闭开关后仍能核验／撤权；原操作者原号恢复不借机读取名单或恢复权限。
- 每次写入重新核对成员、角色、双方 Auth／暂停代次、地点、期限、任职范围、未来时间、版本及重叠；按 merchant→settings→worker→成员／角色／地点既有顺序锁定后判断。
- 原号具有完整意图指纹，包含授权编号、范围、动作与原命令；同号改内容拒绝。界面持久化并核验成功后才发一次 POST，处理同步页面暂停、存储失败和迟到响应。
- 原099／136负责人写入、119模板、140规则核准、166任职操作以及旧归档正文不修改。原负责人仍可取消已暂停员工尚未开始的班次。
- 新接口严格限制 JSON 字段、重复键、UTF-8、体积、读取时限、同源与真实登录身份；响应不缓存，未知错误脱敏。服务角色只有统一 RPC 执行权，没有新表直读写权。
