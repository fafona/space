# 普通员工网页：明确选班与上班原子保存

日期：2026-10-05，第160批。按用户对[159具体接线范围](employee-attendance-clock-schedule-selection-boundary-20261005.md)的批准实施。仅本地，默认关闭；不部署、不配置生产开关、不改真实资料。

## 完整使用路径

- 员工进入原“我的考勤”，先核对当前状态。启用后显示“本次排班”，初始不代选：员工必须选择自己的一个计划，或明确“不关联排班”。
- 候选按当前地点时区的前一天、当天、后一天读取；先用现有员工／日期索引取最多101条原始候选，再核验身份和地点。超过100条或48 KiB时返回“受限”而非伪装没有排班；不自动改用别的计划。
- 新独立接口保持原打卡命令五字段不变，将选择放在外层。137在同一数据库事务内调用原111（原153规则绑定开关独立开启时调用134），保存真实上班和不可变选择结果。必须保存的关联失败时，整笔新上班及可选规则依据一起回滚。
- 成功页面分别显示真实打卡与选择结果。可读取当前已获授权的最近上班编号；不是自由输入他人的编号，也不自动读取所有历史。
- 一个计划允许关联多个实际工作时段；一个原上班事件只有一份初始选择。同一原号重试不能换选择。旧编号无关联时明确显示缺失，不补写历史。

## 结果含义与边界

| 结果 | 含义 |
| --- | --- |
| 已保存选择 | 员工主动选择的本人计划及当时身份依据已保存；不证明本人在现场或出勤正常。 |
| 不关联排班 | 员工明确选择不关联，真实上班照常记录。 |
| 待核验 | 本人计划已取消、缺发布身份依据、地点已变或超出日期窗口；保留真实打卡，不猜测替代计划。 |
| 拒绝 | 他人／不存在的计划、历史已知身份不匹配等；不返回他人详情，不新增打卡。 |

同一日期窗口不代表提前／迟到关联政策；本批没有自动时间匹配、拆分工作时段、迟到／早退／缺勤计算、计划开始规则冻结、工时／工资／导出改造。后来取消计划只显示当前已取消，不改写原选择或撤销打卡。136发布时依据与133实际开班规则依据含义不同，不要求两个时点版本相等。

## 恢复及开关

- 新待确认编号独立存在当前标签页的sessionStorage，按商户和员工分区，包含原命令及原选择。存储不可用／被替换则停止新写入；不清空未知编号。
- 原普通打卡、选班上班、定位待确认相互阻止新写入；先核对原编号。只读核对仍可用，不自动POST。收据为空不代表没提交；只有有效原号收据或严格更新的序列证据才可处理该待确认状态。
- 隐藏、卸载、换身份、旧父鉴权拒绝时清除可见资料并忽略迟到响应；原编号保留。断网恢复先GET，再由用户决定是否按原号重试。
- `NEXT_PUBLIC_FAOLLA_ATTENDANCE_SELF_SCHEDULE_ENABLED=1` 控制新页面入口；服务端还必须同时配置 `FAOLLA_ATTENDANCE_SELF_SCHEDULE_ENABLED=1` 和明确的 `FAOLLA_ATTENDANCE_SELF_SCHEDULE_SITE_IDS` 商户名单。均未在本批配置。
- 关闭独立选班开关后，未确认的新编号只能走新接口GET恢复，不降级到旧POST。没有新待确认且服务端确认未开放时，原普通上班入口保留。原SELF总开关关闭仍404，不能用恢复接口绕过总开关或当前权限。
- 原 `FAOLLA_ATTENDANCE_RULE_BINDINGS_*` 开关保持独立；本批不替它开启，不改变其他三种打卡通路。

## 数据与发布约束

候选迁移137依赖111、134、136及其前置；仅新增一张私有追加关系表和三个函数，不改旧函数／表／索引、原事实或迁移运行器。关系表没有客户端直接权限，只有新RPC供service_role执行；快照大小有界，不复制整份排班或规则原文。公开响应不含员工Auth、私有发布／取消快照，64 KiB上限。

未来试点仍须先建立专用测试商户／员工，核验真实登录与跨身份、浏览器刷新与断网、开关回退、手机布局和真实Next／PostgREST路径；再按无维护候选发布方式考虑上线。本地合成认证和直连SQL不冒充这些验收。

## 本地验收

167项定向回归（91项新测试）、全量TypeScript、17文件ESLint、138份迁移目录检查通过；135个受保护旧文件指纹不变。原SelfPanel仅做获准的入口、恢复互锁和鉴权清屏接线，其余旧控制器和三种其他打卡服务未改。

复用已有停止的本地PG15，在同一所有权校验的临时schema通过9组实际处理器／服务／SQL及4组实际父组件浏览器验收，包括：

- 4组由精确阻塞PID确认的双连接竞争：取消先发生、上班先发生、同原号同时提交、同序列不同原号。没有把延时或顺序调用当作锁证据。
- 实际强制关联表写入失败后，在外层清理前核验新事件、可选规则绑定／来源及新关联均未留下。
- 本人无136依据、已取消计划、多人／多商户／身份换绑、跨午夜计划、同计划多个工作时段、旧原号不补采、101候选限额和私有权限／不可变约束。
- 实际SelfPanel在390px宽度下明确选择none和slot；合成恶意地点名作为文本显示，无横向溢出。前端默认关闭时不额外调用新接口。
- 真实提交成功后丢弃响应，刷新仅GET原号恢复且不重复POST；未送达的原号在关闭前后端新开关后保留，只读核对，不走旧上班。重新开启并明确重试才按原号GET→POST。

原生主检查为26条合成事件／12条新关联／1条规则绑定／1份规则来源；页面增加8条事件和4条关联，最终34／16／1／1。所有非目标合成事实和旧定义／授权未变，临时schema清理、基线恢复、集群停止均已确认。不新建集群或安装依赖，不做完整生产构建，不留浏览器测试服务器。

联调实际发现并修复了两类问题：普通GET的空选择参数被误当成原选择为none，导致已有选班收据被拒；137新增guard中CASE表达式需括号以避免PL/pgSQL解析歧义。另收紧新子组件父鉴权拒绝清屏，以及旧GET在途时确认后刷新必须等待完成；对应回归已补。测试不等于真实Auth／Next／PostgREST／手机试点，也未重测另外三种打卡设备通路。

固定24项盘点暂仍为16项限定本地已有／6项部分完成／2项未实现；普通网页明确选班仅推进正式关系的一部分，不将整体P1宣布完成。
