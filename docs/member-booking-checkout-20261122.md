## 已实现的第一阶段

- `merchantCheckoutCatalog.ts`：独立稳定项目 ID、明确的服务/商品绑定、报价版本、数量、预约时段引用；
  拒绝浏览器传入金额、积分、会员身份和“已付款”标记。缺少价格不视为免费。
- `merchantCheckoutQuote.server.ts`：只读、依赖注入的服务层；新功能默认关闭，检查发布源和模块权限；
  会员仅按可信账号 / 用户 ID 绑定，不按邮箱匹配。只返回本人可用积分，不返回会员 ID、联系方式、Stripe 账户或收费政策。
  金额/费率未确认、商户收款能力未就绪、积分不足时对应方式不可用。查询不占位、不扣款、不扣积分。
- `merchantSettlement.ts`：结算状态与预约/订单业务状态分离；现金与积分分开；
  退款、争议、未知付款和已关闭的单据不会自动重新变为可扣款。固定、比例定金和尾款仅按可信原单金额计算。
- `merchantPointsCheckoutProtocol.server.ts`：新增会员自助结算协议；账号 / 商户 / nonce 唯一绑定操作，业务选择绑定不可变指纹。
  每次尝试只允许一个原子写 RPC；明确的无写入 CAS 冲突最多重算三次，超时/未知结果不自动补偿或重扣。
  每次查询、重放、提交及返回前核验身份。异步计划超时后不得继续发起迟到写请求。
- 两个共享界面组件：结算方式选择、后台结算标签；中英西语、手机与电脑布局；
  没有控制器回调时付款按钮禁用。组件不会调用 Stripe 或积分接口。
- `database/proposals/20261122_member_checkout_design.sql`：仅用于隔离测试的私有表设计；
  稳定版本、商户范围关联、原单唯一绑定、积分/金额单位隔离、凭证去重、不可修改的历史、取消后不可重开。
  RLS 默认拒绝，浏览器/API 角色无直接权限，没有公开 RPC 或 SECURITY DEFINER。

## 下一阶段：真实业务闭环

### A. 项目绑定与可信报价

1. 预约目前主要使用文本选项。需要商户显式配置稳定服务 ID / 兑换项目映射，不能自动按名称猜配。
2. 后台提供新设置，负责人确认后保存；不自动改写既有设置，不批量替客户填价格。
3. 模块门禁同时检查预约/商品、会员与积分兑换权限；商户停用、用户暂停/未验证时拒绝新的金融操作。
4. 会员可用积分必须按现有到期、冻结/占用及已兑换规则**只读计算**；不能把原始余额字段当作一定可花的积分。
5. 下单保留价格、费率、数量、取消政策和源版本快照。改价/退会/下架后重试先核对原操作，不重建原单。

### B. 原子兑换数据库桥

1. 在原预约活动代次、全局 CAS 和暂停门禁下，设计新的组合事务；同时取得原会员/库存锁，固定全局锁顺序。
2. 原子事务内重新验证真实身份映射、模块/项目权限、积分有效性、余额/版本、名额/库存及原操作。
3. 一次写齐会员流水、库存/名额、预约/订单、结算凭证和原幂等结果；任意失败全部回滚。
4. 原预约存储是全局文档，**不能把整个预约文档塞入新的 256 KiB 协议**。
   应在原 CAS / 活动代次下校验并应用受限的本单差量，证明其他商户、历史预约和原命令登记未变。
5. 积分/等级/优惠券/消费统计沿用经确认规则；不能因自助兑换重复赠分或多计现金消费。
6. 用真实 PostgreSQL 多连接验证最后一个名额/库存、余额争抢、取消/提交竞争、原收银并发、进程中断与结果恢复。
7. 明确权限与备份/兼容回退后，另行申请正式迁移和启用；第一阶段 SQL 不进入正式迁移工具。

### C. 接入用户端和商户端

1. 新建会员自助 API，身份来自现有认证会话；不接受浏览器指定会员/操作者，不开放商户收银接口。
2. 在预约/产品模块接入共享结算组件；保存同一操作 nonce，未知结果读取原单，禁止重扣。
3. 在预约管理、订单管理和用户订单/预约详情读取同一结算记录；增加过滤、导出和权限脱敏。
4. 保留旧人工确认；付款/兑换不会自动把服务标记为完成。自动确认需明确项目设置及容量校验。
5. 取消/改期分别处理资源和财务：可退积分只返一次，现金退款必须确认结果，已退款原单不重新收费。

### D. Stripe 沙箱与上线

1. 接续原沙箱工作：Connect 商户直收、完整订单款、预约全款/固定定金/比例定金/主动补尾款。
2. 服务端持久通知队列、验签、同账户反查金额/币种/归属、事件与付款凭证去重，拒绝过期单抢占名额。
3. 完整/部分退款、失败/处理中、平台费退款政策、拒付与对账；不得只靠成功跳转页标记付款。
4. 首轮仅对已核验 EUR 结算账户开放 EUR；最低金额采用本试点的保守限制。其他结算币种需另验渠道最低金额与换汇规则。
   未定抽成不是已批准 0%；正式收款保持关闭，待规则确认及真实 Stripe 沙箱手机链路验收。
5. 完整 CI、独立候选、数据库备份及兼容回退验收完成后，另行授权灰度启用。

### 真实 PostgreSQL 组合提案的边界

`database/proposals/20261122_member_checkout_bundle.sql` 只属于私有隔离设计，不进入正式迁移列表，不是生产 RPC。
没有 SECURITY DEFINER、公开授权或应用适配器；anon/authenticated/service_role 均无访问权，试点表默认关闭。

提案在固定锁顺序下组合原 045/046/211/212/213：原预约全局活动代次/CAS → 原会员/订单共享锁，
服务端重读并校验原页面版本，只更新目标会员、新单及指定库存/券，其他商户的预约与历史 JSON 原样保留。
请求只携带新单及版本/差量，不携带整个全局预约文档；后续建单失败会回滚会员、券、库存、历史和幂等结果。
私有结果保存实际生成的券核销事件 ID 及原退券政策，重试只返回原结果；旧积分 v1 协议继续拒绝用券，不作非原子降级。

仍缺少并必须先完成：可信发布源/容量/项目/权限准备、会员过期积分与等级/赠分的完整既有规则适配、
正式组合快照/提交接口、取消/改期/退积分/退券的持久一次性事务、商户项目设置和用户/后台页面接线、正式 ACL/兼容回退与迁移验收。
第二阶段时提案只允许新事务 balanceDelta/growthDelta 为 0；第三阶段已补充现有积分/成长值规则的准备和隔离提交验证，第四阶段进一步验证取消时撤回原消费成长值，见下文。
仍不能把已有会员余额误限为单笔试点金额上限。

## 第三阶段：商户配置及现有会员规则（2026-11-22）

### 本地完成

- 新增 `/admin/checkout?siteId=...` 设置页面和 `/api/merchant-checkout/configuration` GET/PUT。
  必须是当前经核验的商户负责人；默认试点关闭，页面返回 404、API 拒绝；没有加入旧后台菜单或启用试点。
