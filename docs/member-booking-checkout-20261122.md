## 用户确认的实施顺序（2026-11-22 更新）

Stripe 对接延后到其他业务功能接近完成时再做，不作为当前阶段的前置条件。
当前先完成并独立验收以下非 Stripe 范围：

1. 商户预约项目 / 产品的价格与积分设置、稳定项目绑定和可兑换条件。
2. 用户端预约 / 产品结算、本人会员识别、积分余额校验与原子兑换；保留已有到店付款流程。
3. 预约管理、订单管理和用户详情中的结算状态、筛选及记录，业务状态与结算状态分离。
4. 取消 / 改期政策、积分只返一次、重复提交及结果未知时恢复原单、手机 / 电脑完整回归。
5. 上述闭环通过后，才继续 Stripe 沙箱、在线支付、定金 / 尾款、现金退款与支付通知联调。

在第 5 步完成前，不展示可用的在线付款入口，不发起 Stripe 请求，不模拟已付款，也不自动把待付款预约变成已支付或已完成。

## 已实现的第一阶段

- `merchantCheckoutCatalog.ts`：独立稳定项目 ID、明确的服务/商品绑定、报价版本、数量、预约时段引用；
  拒绝浏览器传入金额、积分、会员身份和“已付款”标记。缺少价格不视为免费。
- `merchantCheckoutQuote.server.ts`：只读、依赖注入的服务层；新功能默认关闭，检查发布源和模块权限；
  会员仅按可信账号 / 用户 ID 绑定，不按邮箱匹配。只返回本人可用积分，不返回会员 ID、联系方式、Stripe 账户或收费政策。
  金额/费率未确认、商户收款能力未就绪、积分不足时对应方式不可用。查询不占位、不扣款、不扣积分。
- `merchantSettlement.ts`：结算状态与预约/订单业务状态分离；现金与积分分开；
  退款、争议、未知付款和已关闭的单据不会自动重新变为可扣款。固定、比例定金和尾款仅按可信原单金额计算。
- `merchantPointsCheckoutProtocol.server.ts`：新增会员自助结算协议；账号 / 商户 / nonce 唯一绑定操作，业务选择绑定不可变指纹。
  每次尝试只允许一个原子写 RPC；明确的无写入 CAS 冲突最多重算三次，超时/未知结果不自动补偿或重扣。
  每次查询、重放、提交及返回前核验身份。异步计划超时后不得继续发起迟到写请求。
- 两个共享界面组件：结算方式选择、后台结算标签；中英西语、手机与电脑布局；
  没有控制器回调时付款按钮禁用。组件不会调用 Stripe 或积分接口。
- `database/proposals/20261122_member_checkout_design.sql`：仅用于隔离测试的私有表设计；
  稳定版本、商户范围关联、原单唯一绑定、积分/金额单位隔离、凭证去重、不可修改的历史、取消后不可重开。
  RLS 默认拒绝，浏览器/API 角色无直接权限，没有公开 RPC 或 SECURITY DEFINER。

## 下一阶段：真实业务闭环

### A. 项目绑定与可信报价

1. 预约目前主要使用文本选项。需要商户显式配置稳定服务 ID / 兑换项目映射，不能自动按名称猜配。
2. 后台提供新设置，负责人确认后保存；不自动改写既有设置，不批量替客户填价格。
3. 模块门禁同时检查预约/商品、会员与积分兑换权限；商户停用、用户暂停/未验证时拒绝新的金融操作。
4. 会员可用积分必须按现有到期、冻结/占用及已兑换规则**只读计算**；不能把原始余额字段当作一定可花的积分。
5. 下单保留价格、费率、数量、取消政策和源版本快照。改价/退会/下架后重试先核对原操作，不重建原单。

### B. 原子兑换数据库桥

1. 在原预约活动代次、全局 CAS 和暂停门禁下，设计新的组合事务；同时取得原会员/库存锁，固定全局锁顺序。
2. 原子事务内重新验证真实身份映射、模块/项目权限、积分有效性、余额/版本、名额/库存及原操作。
3. 一次写齐会员流水、库存/名额、预约/订单、结算凭证和原幂等结果；任意失败全部回滚。
4. 原预约存储是全局文档，**不能把整个预约文档塞入新的 256 KiB 协议**。
   应在原 CAS / 活动代次下校验并应用受限的本单差量，证明其他商户、历史预约和原命令登记未变。
5. 积分/等级/优惠券/消费统计沿用经确认规则；不能因自助兑换重复赠分或多计现金消费。
6. 用真实 PostgreSQL 多连接验证最后一个名额/库存、余额争抢、取消/提交竞争、原收银并发、进程中断与结果恢复。
7. 明确权限与备份/兼容回退后，另行申请正式迁移和启用；第一阶段 SQL 不进入正式迁移工具。

### C. 接入用户端和商户端

1. 新建会员自助 API，身份来自现有认证会话；不接受浏览器指定会员/操作者，不开放商户收银接口。
2. 在预约/产品模块接入共享结算组件；保存同一操作 nonce，未知结果读取原单，禁止重扣。
3. 在预约管理、订单管理和用户订单/预约详情读取同一结算记录；增加过滤、导出和权限脱敏。
4. 保留旧人工确认；付款/兑换不会自动把服务标记为完成。自动确认需明确项目设置及容量校验。
5. 取消/改期分别处理资源和财务：可退积分只返一次，现金退款必须确认结果，已退款原单不重新收费。

### D. Stripe 沙箱与上线

1. 接续原沙箱工作：Connect 商户直收、完整订单款、预约全款/固定定金/比例定金/主动补尾款。
2. 服务端持久通知队列、验签、同账户反查金额/币种/归属、事件与付款凭证去重，拒绝过期单抢占名额。
3. 完整/部分退款、失败/处理中、平台费退款政策、拒付与对账；不得只靠成功跳转页标记付款。
4. 首轮仅对已核验 EUR 结算账户开放 EUR；最低金额采用本试点的保守限制。其他结算币种需另验渠道最低金额与换汇规则。
   未定抽成不是已批准 0%；正式收款保持关闭，待规则确认及真实 Stripe 沙箱手机链路验收。
5. 完整 CI、独立候选、数据库备份及兼容回退验收完成后，另行授权灰度启用。

### 真实 PostgreSQL 组合提案的边界

`database/proposals/20261122_member_checkout_bundle.sql` 只属于私有隔离设计，不进入正式迁移列表，不是生产 RPC。
没有 SECURITY DEFINER、公开授权或应用适配器；anon/authenticated/service_role 均无访问权，试点表默认关闭。

提案在固定锁顺序下组合原 045/046/211/212/213：原预约全局活动代次/CAS → 原会员/订单共享锁，
服务端重读并校验原页面版本，只更新目标会员、新单及指定库存/券，其他商户的预约与历史 JSON 原样保留。
请求只携带新单及版本/差量，不携带整个全局预约文档；后续建单失败会回滚会员、券、库存、历史和幂等结果。
私有结果保存实际生成的券核销事件 ID 及原退券政策，重试只返回原结果；旧积分 v1 协议继续拒绝用券，不作非原子降级。

仍缺少并必须先完成：可信发布源/容量/项目/权限准备、会员过期积分与等级/赠分的完整既有规则适配、
正式组合快照/提交接口、取消/改期/退积分/退券的持久一次性事务、商户项目设置和用户/后台页面接线、正式 ACL/兼容回退与迁移验收。
第二阶段时提案只允许新事务 balanceDelta/growthDelta 为 0；第三阶段已补充现有积分/成长值规则的准备和隔离提交验证，第四阶段进一步验证取消时撤回原消费成长值，见下文。
仍不能把已有会员余额误限为单笔试点金额上限。

## 第十二阶段：到店付款与金额券的私有待收款内核（2026-11-23）

- `merchantCheckoutOnSitePending.server.ts` 只接收可信存储提供的配置、本人会员和券记录，复用既有金额／券报价规则：现金、满减、折扣、储值面额券以及明确绑定的商品／项目／时长券；不允许积分券抵现金，不发明金额券叠加或储值券余额钱包。
  EUR 以整数分计算；单次券全额覆盖时明确为 `coupon_covered`，否则为 `unpaid`。两者 `capturedMinor` 始终为 0，`totalPoints` 始终为 null。
  新的 V2 待收款凭证使用白名单投影，不返回会员编号、券领取码、交易历史或原资源私有字段；原 V1 积分解析器不能将它误读成已兑换积分。

- 到店待收款**不改写会员文档**，不扣积分／余额、不做积分过期或等级福利准备、不发消费赠分、不造一笔零额会员交易；无限库存且无券时也不写设置或券文档。

## 第十三阶段：到店原单取消、退券和查询（2026-11-23）

### 根因及独立实现

- 原积分取消器要求原积分交易明细；将现金原单塞入其中，既不符合单位，也可能把取消误作积分返还。保留原取消器和积分提交器不变，增加私有 `cancel_on_site_pending` 与专属查询／适配器。
- 取消只按不可变原操作、原客户、原资源和下单时的退券／提前取消政策执行；不改为读取今天的 offer 政策，也不以商品名称、邮箱、当前所选会员或客户传来的券数量猜测原单。
  新购买关闭、当前 offer 被停用／政策改变、会员后来退会，都不改变原单的取消约定。
- 在原商户结算锁 → 原预约代次控制锁 → 原商户订单／会员锁的顺序下，核对原资源状态、updatedAt 和冻结条款。
  预约／订单取消、有限库存分配释放、原券退回、原单关闭凭证及商户发起人的审计同成同败；最终原写入事务或约束失败会回滚全部先前修改。
  同单重复取消和商户／客户并发取消只生成一份凭证；使用原单重新读取恢复，不自动重试、清除原单或执行反向补偿。
- 退券由原政策决定。只移除原凭证对应、原客户名下、原操作标记的那一笔核销，保存不可变退券证据；不会移除后来独立使用的核销记录。

  不退券政策下券文档不写入；零应收的全券订单也不伪造现金／积分退款。
- 不读取、归一化或写回会员财务文档，不返积分／余额、不赠分、不修改成长等级或重新激活会员。真实原收银事务在取消等待期间修改的会员记录保留原样。

### 诊断与实现

- 原金融内核、不可变凭证和取消器只处理单项目。不能把多商品包装成一个虚假项目，也不能循环调用单品提交：后一种做法会留下部分扣分／用券／占库存成功而整单失败的结果。因此先补独立的只读购物车报价，为之后单事务合单准备可信输入，不把这一阶段冒称为完整购物车结算。
- `merchantCheckoutCartQuote.server.ts` 接收同一商户、同一结算方式（积分或到店）的稳定商品报价 ID／版本、数量，以及明确分配到商品行的本人券领取标识。最多 20 个不同商品、总数量 999、总券数 20；拒绝重复报价、同商品跨电脑／手机别名、重复券、浏览器价格／会员／联系人／时段／财务 token；不自动合并、选择其他结算方式或忽略失败商品。
- 从一份私有原始数据库快照复用单品的发布源、现价、权限、会员、有效积分、券及可用量检查；这里只机械拓宽只读上下文类型，财务提交仍要求原严格 customer／nonce／confirmation 请求。没有伪造联系人或把显示报价拼成财务准备器。
  多商品汇总只扣除一次可用积分预算，按共享 stockItemId 合计库存；生日／到期等只读准备不会按商品行累加到余额。各商品原退积分／退券／截止政策分别保留，不猜一个整单政策。
- 券必须明确分配给某个商品行；门槛按原行规则，不擅自改成整车金额。当前模型没有通用整车叠券规则，因此现金／兑换券仍最多一张；多张积分券只按既有规则，并将“每次兑换最多张数”限制应用到整车，不能拆商品绕过。选中券的原始规则和领取／核销记录必须与解析结果一致，JSONB 属性顺序不同不误判。
- 积分与 EUR 整数分币分别合计并检查原 99,999,999 上限；缺价不是免费，一项不支持所选方式／已下架／报价过期则整车拒绝，不出部分成功。总积分不足返回明确不可用原因。报价输出只白名单商品、数量、折扣、合计与本人可用余额；不返回原始表、私有会员 ID、联系方式、券码、操作 nonce 或可提交的 confirmationHash。
  返回的 quoteHash 只是本人范围的显示指纹，且始终 `previewOnly: true / canSubmit: false / reservationCreated: false / capturedMinor: 0`；没有用显示报价授权扣分、收款或建单。

## 第二十一阶段：实际商品购物车接线与持久化原单确认（本地／隔离）

### 接入前查明的问题

## 第二十二阶段：跨设备原单共同记录与显式确认基础（仅本地／隔离）

### 诊断与实现范围

- 共用 nonce 和 Web Lock 只存在于同源浏览器；另一设备没有原编号时，原服务器并不知道“上一笔是否已由用户核对”。核对发现新账本的单品积分、单品到店和整车，均在同一事务内追加 `bundle_results`，并已有相同商户结算 advisory lock。本轮复用这一个共同追加点，不另改财务写入器或循环单品扣分。
- 新未注册提案 `20261123_member_checkout_pending_intents.sql` 增加默认关闭的站点登记、不可修改的原单代次记录和显式确认记录。启用时，同一商户＋实际账号／用户 principal 的下一笔新账本原单必须等上一笔确认；否则在原财务事务内拒绝，已进行的订单、积分、券和库存操作全部回滚。确认不返分、退券、取消或创建新单，也不标记现金已收。
  新登记关闭后，已有代次的账号仍须核对，不能靠关登记绕过；不存在超时自动确认。切入前存在未登记的新账本原单时明确要求人工核对，不任选“最近一笔”、不自动回填或视为已确认。本轮未改动真实历史数据。
- 本人未决查询不需要设备持有旧 nonce，只返回安全的版本一／二单品或版本三整车展示投影，不返回原始凭证、会员 ID、联系人、券码或请求指纹。与提交使用同一锁，但查询／确认使用非等待式获取：原写入仍在途时返回 busy，不能把旧快照中的空结果当成“没有原单”。拒绝保留旧快照的 REPEATABLE READ／SERIALIZABLE 调用，避免锁已释放后仍读到过期的“无原单”。
- 确认必须携带原操作键、精确代次及当前安全视图的 SHA-256；SQL 在锁内重新核对本人、当前资源和条款。原单需人工核对、视图已变或代次不符时不追加确认。重复确认旧代次只返回旧确认结果，绝不释放之后的新原单。新确认在服务器时限内仅追加一次，失败时整笔元数据回滚。

### 实际购物车的顺序与恢复行为

- `MemberProductCartBlock → MemberCartCheckoutPanel → createCartCheckoutController` 已接入独立新模式：启动、报价前和提交前检查服务器原单；换设备没有本地 nonce 时直接显示本人原单，不伪造编号，也不创建本地财务记录。保留本机购物车和联系人，阻止在未决单上再预览／提交。服务器无响应或数据库登记未就绪时暂停，不当成“没有原单”；已知无写入的联系人校验错误仍可直接修改，不虚构待处理财务单。
