# Faolla 员工考勤：产品、技术与上线计划

版本：规划稿 v1.0 · 2026-09-29

状态：本文保留规划基线，不再复制会滞后的逐批进度。当前完成度、证据边界及有限的剩余交付见 [固定进度台账](employee-attendance-progress-20261004.md)；逐批证据见 [实施记录](employee-attendance-implementation-20260929.md)，真实环境、身份与设备准备见 [试点清单](employee-attendance-pilot-readiness-20261002.md)。用户暂未准备专用真实测试账号，当前先完成本地验收。**考勤候选仍默认关闭、未部署；合成认证／传输不等于真实认证、手机或生产网络已通过，整体P1尚未完成。** 不因本地测试数量增加而替代真实试点，也不将已完成的局部主链重复列为待实现。

## 1. 方案结论与实施边界

在现有「企业管理」下新增「员工考勤」，使用一套员工身份、打卡事实、工时计算与审批体系，支持多个采集入口。不要为手机、实体卡、工牌分别做三套考勤系统。

推荐顺序：

1. 先交付可完整日常使用的手机／网页、门店动态二维码和终端 PIN 考勤，包含班次、休息、补卡、审批、报表。
2. 再接经过实机验证的二维码工牌、RFID／NFC 卡与固定终端离线补传。
3. 按实际需求扩展复杂轮班、调休余额、外部薪资接口、原生手机凭证。
4. 人脸、指纹、持续定位、自动工资处罚不进入默认产品范围。

规划假设：首批以西班牙商户为主要试点，允许多个门店、兼职和分段班；以后通过国家／地区规则配置扩展。实际雇佣国家、行业集体协议、规模、设备尚待确认，不能据此声称已经满足全部劳动法要求。

三个必须分开的概念：

- **实际记录**：员工什么时候提交了什么打卡，以及补正之前的原始事实。
- **管理确认**：补卡是否核实、额外工时如何审核、哪些异常仍有争议。
- **薪资结算**：是否支付、支付标准、税务及工资单；需要当地规则和薪资系统，不直接等同于打卡时长。

## 2. 市场参考：借鉴什么、不照搬什么

以下是查阅官方文档确认的能力，不代表所有版本、订阅或设备都支持。

| Odoo Attendances | 终端与个人入口；主管权限范围；缺失记录处理；额外工时审批及部分批准 | 多入口共用考勤账本；审批与实际工时分开；主管只管授权员工 |
| Factorial | 网页、手机、员工 ID、现场二维码；定位策略；手机 App 离线记录与同步 | 按考勤组设置方式；定位只在打卡时采集；同步失败要有明确状态 |
| Microsoft Shifts | 上下班、休息起止、本人查看与确认、团队工时导出 | 员工端动作简单；本人能核对；确认后的修改有明确流程 |

对应来源：[Odoo 权限与配置](https://www.odoo.com/documentation/19.0/applications/hr/attendances.html)、[Odoo 审批](https://www.odoo.com/documentation/19.0/applications/hr/attendances/management.html)、[Factorial 打卡方式](https://help.factorialhr.com/en_US/time-tracking/about-time-tracking-systems)、[Factorial 定位](https://help.factorialhr.com/en_US/time-tracking/how-to-use-geolocation-in-time-tracking)、[Microsoft Shifts](https://support.microsoft.com/en-gb/teams/shifts/clock-in-and-out-with-shifts)、[Deputy 工时表模型](https://developer.deputy.com/docs/timesheet)。

下面的 Faolla 设计是结合现有项目提出的方案，不宣称上述平台都采用同样实现。尤其不照搬自动补下班、自动扣休息、修改后覆盖原始记录等可能引起争议的默认行为。

## 3. 现有项目可以复用和必须新增的部分

### 3.1 可以复用

- 企业成员关系、邀请、员工登录、多企业切换。
- 角色权限目录、服务端逐请求授权、企业审计的设计方式。
- 商户端现有 UI、待办／通知入口、语言与日期展示基础。
- 当前数据库、应用服务和经审查可复用的后台任务基础设施。

核对依据：`src/lib/merchantEnterprise.ts`、`src/lib/merchantEnterpriseAuth.server.ts`、`src/app/api/merchant-enterprise/employees/route-handler.ts`、`docs/merchant-enterprise-employee-foundation.md`。

### 3.2 必须新增

- 考勤人员档案、工作地点、考勤组、规则版本、班次与排班。
- 打卡事件、工作时段、休息时段、异常、补正申请、工时表及锁定版本。
- 考勤终端、员工凭证、设备授权和受控离线协议。
- 独立考勤查询及聚合，不能把它塞入现有企业全量 overview snapshot。

### 3.3 必须保持的现有边界

- `siteId`／数据库 `merchant_id` 是授权租户边界；一个考勤「工作地点」不是新的租户，也不是任务看板。
- 不因为同一真实老板有多个商户账号，就自动合并这些账号的员工和考勤数据。
- 不把普通商户账号直接改成员工专用身份；沿用现有身份安全边界。
- 停用某企业员工，只影响该企业；不能把其其他企业的登录与记录一起撤销。
- 当前没有完整部门／上下级关系。首版采用工作地点和明确员工名单授权；需要部门树时单独建设。
- 用户登录、页面在线、任务完成、订单操作不能充当打卡事实。

## 4. 功能分层和菜单

### 4.1 普通员工

入口：企业管理 → 我的考勤；手机工作区提供显著快捷入口。

- 今日打卡：当前企业、工作地点、班次、当前状态、上一次确认结果。
- 我的记录：日历／列表、当日完整时间线、休息、异常、原始与补正后的记录。
- 我的申请：补卡、更正、外勤／远程、请假及审批进度。
- 我的工时表：周期汇总、待确认、争议提交、下载本人记录。
- 我的凭证：已绑定工牌状态、挂失；不显示完整密钥或其他员工凭证。

### 4.2 主管／商户管理员

企业管理 → 员工考勤，二级页面建议：

1. 今日概览。
2. 考勤明细。
3. 班次与排班。
4. 申请与异常。
5. 工时表与报表。
6. 考勤人员与考勤组。
7. 工作地点。
8. 设备与工牌。
9. 考勤设置。

桌面页共用顶部企业、地点、日期、人员筛选；列表状态和筛选保留，但切换企业立即清理旧数据。批量操作先预览影响对象，不默认选中全企业。

### 4.3 超级后台

- 按商户开通考勤模块、允许的入口和设备接入能力。
- 配置人数、地点、终端额度；额度下降不删除既有数据，也不静默阻止已在考勤员工完成下班。
- 查看模块健康度、错误率、设备在线数量和用量，不默认读取全平台员工精确位置。
- 支持授权、限时、留痕的故障协助；不得存在隐藏的「代员工打卡」万能入口。
- 功能暂停与历史资料读取分开设计：保留受控档案访问／导出，不能靠绕过当前授权实现。

## 5. 打卡方式与真实能力边界

| 方式 | 员工操作 | 设备与前提 | 风险和处理 | 阶段 |
| --- | --- | --- | --- | --- |
| 手机网页／PWA | 登录后点击上下班／休息 | HTTPS、网络；定位需授权 | 账号共享、设备时间不可信；以服务端时间为准 | P1 |
| 手机定位打卡 | 点击后采集一次位置 | 支持定位的设备、权限 | 室内误差、模拟位置；不能保证人在现场 | P1 |
| 手机扫门店动态码 | 登录后扫描现场屏幕码 | 已绑定终端、摄像头或系统扫码 | 码短时有效仍可能被实时转发 | P1 |
| 门店终端工号＋PIN | 输入工号及个人 PIN，选动作 | 平板／电脑固定终端 | 防猜测、遮挡、限速；工号本身不是密码 | P1 |
| 二维码／条码工牌 | 在门店扫码器前出示工牌 | 支持该码制的扫码器／摄像头 | 静态码可复制；绑定终端、可选 PIN | P2 |
| RFID／NFC 实体卡／工牌 | 刷卡后确认动作 | 指定卡种、读卡器、协议适配 | UID 可克隆、卡可转借；明确安全等级 | P2 |
| 员工手机动态码 | 员工亮码，门店终端扫描 | 已登录手机、受信终端 | 短时一次性凭证、绑定企业员工与终端场景 | P2 |
| 手机碰 NFC 标签 | 碰门口标签打开打卡页 | 兼容设备／标签 | 静态链接只作入口，不证明到场 | 可选入口 |
| 手机代替 NFC 门禁卡 | 手机靠近读卡机 | 原生应用／系统权限／厂商凭证方案 | 不能靠普通网页通用实现 | 专项验证 |
| Wi-Fi／网络限制 | 到指定网络后打卡 | 企业网络配置 | 公网 IP 不等于 SSID、也不等于真实在场 | 辅助条件 |
| 蓝牙／近场设备 | 手机与现场设备交互 | 原生兼容性和设备验证 | 浏览器及后台限制、转发风险 | 后续专项 |
| 指纹／人脸 | 专用终端识别 | 合法性评估、设备及安全方案 | 高敏感数据；不默认启用 | 独立审批 |

Web NFC 目前文档说明的范围是 Android Chrome 的 NDEF 读写，不支持通用低层卡协议或 HCE 卡模拟。因此「手机能读 NFC」不等于「手机能当员工卡」，更不等于所有 iPhone／Android 浏览器均可用。[Chrome 官方能力说明](https://developer.chrome.com/docs/capabilities/nfc)

所有入口都不能承诺 100% 防代打。选择适当的身份、现场证据和异常核查组合，并提供不使用个人手机也能完成打卡的终端入口。

## 6. 员工身份、考勤档案与生命周期

考勤对象使用独立稳定 `workerId`，归属于当前企业；可关联一个现有员工 membership，但不强迫每位刷卡工人拥有邮箱账号。

档案最小字段：姓名／显示名、企业内工号、在职起止日期、考勤参与状态、默认地点、考勤组、审批负责人、可选 membership 关联。证件号码、家庭地址、工资、健康证明不属于默认必填字段。

两个典型路径：

- 有员工账号：经显式确认把考勤档案关联到现有 membership，保留现有角色和邀请链。
- 仅终端打卡：建立考勤档案、发 PIN／工牌，不创建虚假邮箱或共享登录账号；员工个人查询可通过后续邀请绑定或受控资料获取流程完成。

生命周期：

1. 新建档案，确认是否已经存在同一人，不能只按姓名自动合并。
2. 指定开始日期、地点、考勤组、审批人。
3. 发凭证；首次 PIN 设置或改密，不显示可回读明文 PIN。
4. 调店／换班／规则变更均有生效日期，不静默改写历史。
5. 挂失即时撤销在线凭证；替换卡保留旧卡有效区间和归属历史。
6. 离职停用打卡授权、卡和设备关联，但保留依法应保存的考勤。
7. 停用时若仍有未结束时段，生成管理员待处理事项，不自动把停用时间当下班。
8. 再入职新建在职区间，不复用已撤销卡或误合并不同工号持有人。

员工账号停用与劳动关系终止不是同一个业务事实。已关联 membership 的考勤人员，默认随该企业 membership 停用而停止所有新的打卡入口，包括终端；未结束时段进入受控补正流程。若确需改为仅终端考勤人员，必须经有权管理员单独确认身份和授权、显式重新配置并留痕，不能因为卡仍存在就自动形成旁路。

## 7. 手机打卡页与交互

首屏只显示必要内容：企业／门店、当前当地时间与时区、班次、当前工作状态、主要操作和最后成功记录。不要先加载全部员工、全月明细或地图 SDK。

动作：上班、开始休息、结束休息、下班；允许多段班，按钮随服务端当前状态变化。

一次打卡流程：

1. 读取当前企业身份和本人状态，确认地点、动作。
2. 规则需要时获取一次定位或扫描现场码；告诉员工为何需要。
3. 建立稳定操作编号并提交。
4. 服务端重新授权、校验方式和规则，原子写入后返回记录号和确认时间。
5. 页面显示「已记录」或「已记录，待核实」；不能把按钮按下、动画完成或本地缓存写入当作服务端成功。

超时显示「结果待确认，正在查询」，以原操作编号查收据／重试；不立刻换编号重复打卡。明确区分「未提交」「本机待同步」「服务器已记录待审核」「已确认」。

网页能力：摄像头／定位权限被拒时显示可操作的替代入口；内置浏览器不兼容时允许外部浏览器打开并重新安全登录。不能把无法检测的设备能力显示为已经通过。

无障碍：按钮足够大、有文字状态、不仅靠颜色；支持键盘与读屏、24 小时制和当前项目已有语言。倒计时本地展示，不每秒请求服务端。

## 8. 门店终端与二维码安全

### 8.1 固定终端

- 管理员生成短时配对码，在指定平板／电脑配对；设备获独立、可撤销、仅考勤范围的凭证。
- 不保存老板密码，不下发数据库 service-role 密钥，不允许通过终端读取全员联系方式或管理后台。
- 绑定企业和地点；迁店需要重新授权；退出终端管理需管理员验证。
- 屏幕显示网络状态、时钟校验、最近同步状态；成功提示数秒后清除个人信息。
- 默认不列出完整员工名单；通过工号＋PIN／凭证识别人，错误提示防止批量枚举。
- 不承诺网页能限制整个操作系统；需要时使用设备自带的 kiosk／锁定模式并验证。

### 8.2 两种动态二维码不混用

- **现场码**：由已绑定门店终端展示，多名员工可在有效期内各自使用。校验企业、地点、终端和过期时间；对每个员工的操作去重，不能让第一位员工扫描后整张门店码失效。
- **员工码**：表示某员工短时凭证，指定用途，可由授权终端消费；一次消费原子化，防止截图反复使用。

有效期建议从 30–60 秒范围试验，按现场扫码体验调整；这是候选参数，不是已上线规则。必须在服务端验签、检查终端当前授权，过期终端不能离线长期铸造有效码。

静态名片码、公开链接和现有名片行业外框均不复用为打卡凭证；可复用普通二维码渲染能力，但不能把考勤密钥放入公开名片或通用导出。

## 9. 定位规则

工作地点保存经管理员确认的位置中心、半径、地址及 IANA 时区；定位不要求使用付费地图，地图仅在配置／有权核查时按需加载。

考勤组可选择：不采集位置、采集并提示、范围异常待审核、严格现场认证并提供替代申报。严格模式也必须有记录实际工作声明的渠道，不能让技术失败抹去事实。

一次提交记录定位获取时间、精度、规则版本和判定。处理：

- 明确范围内：按规则通过。
- 明确范围外：提示距离与原因，按策略转外勤／待核实，不默认判旷工。
- 精度覆盖边界、旧坐标、无法定位：视为不确定，不装作精确验证成功。
- 拒绝权限／手机没电：终端打卡或补正；不要求开启全天定位。

仅在本人发起打卡时采集。原始坐标与工时事实分离，精度／范围判定也属于个人数据；限定访问和保留期限。不以浏览器检测脚本声称可靠识别所有 GPS 伪造。

HTTPS 与用户授权是网页定位的基础条件，但不能保证室内精度或硬件来源。[Geolocation API](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation_API)

## 10. 排班、考勤组和规则版本

### 10.1 首版覆盖

- 固定班、每周重复班、每日临时班。
- 一天多段：例如 10:00–14:00 和 17:00–21:00。
- 跨午夜：例如 22:00–次日 06:00。
- 无固定班的工时记录：可打卡，但不无依据计算迟到／缺勤。
- 全职／兼职不同应出勤计划；资格和规则由管理员配置，不推断劳动合同。
- 简单请假、出差、远程工作区间与节假日／停业日配置。

### 10.2 后续扩展

循环轮班、换班申请、开放班次、岗位覆盖人数、多个审批层级、调休余额、年度工时平衡、外部工资软件映射。自动排班另立项目，不能只为赶功能加入难以审计的自动决策。

### 10.3 规则字段

每个考勤组配置允许方式、地点范围、班次来源、迟到／早退宽限、休息类型、异常阈值、补正申请窗口、审批人、工时表周期和提醒。

宽限只影响分类或经确认的结算规则，不改写原始到离时间。无排班不自动判缺勤；在请假期间打卡需核查冲突；临时加班不因未预批而拒绝保留真实起止记录。

配置采用草稿 → 验证 → 定时／即时生效，留存操作者、原因和版本。规则优先级要显式：经批准的个人例外 → 生效中的考勤组 → 企业默认；地点限定和授权是另一个必须同时满足的维度。

历史计算使用当时规则和排班快照；修改规则默认仅影响未来。追溯重算必须预览影响、说明原因、经授权产生新结果版本。

## 11. 时间和工时计算：先保证不算错

### 11.1 时间基准

- 在线事件以服务器提交事务的 UTC 时间为权威；客户端时间仅供诊断。
- 工作地点／排班具有权威 IANA 时区，如 `Europe/Madrid`；浏览器改时区不改所属工作日。
- 同时保存原始 UTC、采用的时区及需要的计算上下文；报表可展示当地时间和偏移。
- 跨午夜班次有班次归属日；工作时段也能按实际自然日／结算周期切分，不能重复计时。
- 夏令时切换按实际时间间隔计算；重复或不存在的手填当地时间需明确偏移或拒绝模糊输入。
- 多时区外勤使用明确的班次时区政策；不能根据员工手机旅行地点随意迁移历史日期。

### 11.2 状态转换

| 当前状态 | 操作 | 结果 |
| --- | --- | --- |
| 未在工作 | 上班 | 开始一个工作时段 |
| 工作中 | 开始休息 | 开始一个有类型的休息时段 |
| 休息中 | 结束休息 | 结束休息，恢复工作 |
| 工作中 | 下班 | 结束工作时段 |
| 休息中 | 下班 | 明示是否同时结束休息；确认后原子记录两个动作 |
| 任意状态 | 重复同一操作 | 返回同一收据，不新增第二次业务事实 |
| 任意状态 | 与状态不兼容的操作 | 保留必要尝试信息／提示纠正，不盲目切换上下班 |

同一企业的同一考勤人员最多一个进行中的工作时段。跨门店可按规则在其他授权地点结束同一时段；两个不同企业不互查私人工作记录来强行阻止重叠。

### 11.3 计算口径

- 出勤跨度：工作开始至结束的实际时间。
- 实际工作时长：跨度扣除实际记录的全部休息；有缺口时标记不完整。
- 计入工时的时长：按明确规则对带薪休息、培训等进行分类；不能直接当工资金额。
- 计划工时：来自生效排班，独立于实际打卡。
- 额外工时候选：按当地合同和规则计算，不能一律「实际减计划」。
- 已审核额外工时：审核结果，原始记录和争议仍可见；拒绝审批不等于法定无需支付。

例：09:00–18:00，记录 1 小时午休和 15 分钟休息，则实际工作为 7 小时 45 分钟；若后者按有效规则计入工时，相关统计可为 8 小时。两列要标清，不能互相冒充。

不默认自动扣 30／60 分钟午休；不默认到排班终点自动生成下班。超长未结束时段标为异常，待员工／管理员补正，不无限累计成已确认工时。

## 12. 补卡、异常、请假与审批

### 12.1 异常分类

漏上班、漏下班、重复／相互矛盾的动作、定位不确定、异地打卡、未排班工作、请假与打卡重叠、超长工作、过短休息、离线时间不可信、设备重复序号、已锁周期补传、已撤销凭证补传。

异常是核查事项，不自动等同于员工违规。界面展示原因、证据可靠性和可执行处理路径。

### 12.2 补正流程

1. 员工选择日期／时段，填写实际开始／结束及原因；界面展示修改前后的差异。
2. 系统检测重叠、时区歧义、审批期限、是否涉及锁定周期。
3. 发送给授权审批人，员工不能默认审批自己的申请。
4. 审批人批准、驳回或退回补充；所有结果带说明和操作时间。
5. 批准后追加补正事件，重算受影响人员与日期，通知本人。
6. 已审批申请不可直接编辑；撤回／更正通过新申请或冲正记录。

小微企业确实没有第二审批人时，可配置企业主自确认例外，显著标识并审计；不得隐式让所有管理角色自批。

### 12.3 审批可靠性

- 同一申请版本最多成功处理一次；两位主管同时点击不能覆盖结果。
- 审批时重新校验当前授权范围，不能依赖创建申请时的权限。
- 审批人离职／撤权时转交给有效负责人并留痕，不能无人处理。
- 不因为超时未审批就默认批准；提醒合并、频率受限。
- 员工看到原始与修订结果，并可提出异议；不把「未提出异议」默认为同意所有变更。
- 病假首版仅记录必要类别和区间，不在考勤系统默认收集病历／诊断附件。

首版请假作为排班和考勤冲突的必要输入；复杂法定假期余额、累计与跨年规则后续单独实现，不伪造完整 HR 系统。

## 13. 工时表、报表与导出

推荐支持：当日实时概览、员工日明细、周期工时表、迟到早退和漏卡清单、补正／审批记录、地点汇总、打卡方式统计、设备异常统计。

报表字段按权限选择：人员及工号、地点、归属日、班次、实际起止、多段休息、工作时长、计入工时时长、计划工时、额外工时及审核状态、来源方式、补正状态、计算版本。精确经纬度、完整卡号不默认进入导出。

工时表状态：开放 → 待核对 → 已确认／有争议 → 已锁定 → 经授权重开 → 新修订版。锁定不删除事实，补传不得悄悄改变已经导出的工资依据。

首版 CSV 和打印友好明细；后续按需求增加 XLSX／PDF 及工资软件模板。导出必须：

- 服务端重新授权并限定企业、人员和日期范围。
- 大范围后台生成，分批读取，限制并发，不全表装入内存。
- 保留字段口径、时区、生成时间、修订版本；处理 CSV 公式注入。
- 私有下载、短时有效、可审计；链接生成和下载时检查适用授权，不能因分享公开 URL 泄露。
- 对离职员工仍能按合法权限导出保留期内历史；停用账号不抹掉记录。

历史导入分阶段：先模板检查、试算、重复识别、差异预览，再明确确认写入；标为外部导入，记录批次和来源，绝不自动当成设备原始事实。

## 14. 权限与数据范围

同时检查「商户是否开通」「操作者拥有什么动作权限」「能操作哪些人员／地点」「当前记录状态」。前端隐藏按钮不是授权措施。

建议新增权限族（名称为设计稿）：

| 权限 | 能力 |
| --- | --- |
| `attendance.self.clock` | 本人打卡 |
| `attendance.self.view` | 查看本人记录；不自动授予导出 |
| `attendance.self.export` | 单独授权导出本人完整可见工时，依赖本人查看 |
| `attendance.self.request` | 本人申请和异议 |
| `attendance.records.view` | 查看授权范围明细 |
| `attendance.schedule.manage` | 管理排班 |
| `attendance.requests.approve` | 审批补正／请假等 |
| `attendance.overtime.approve` | 审核额外工时 |
| `attendance.timesheets.close` | 确认／锁定周期 |
| `attendance.timesheets.reopen` | 重开锁定周期，较高风险 |
| `attendance.reports.export` | 导出授权范围报表 |
| `attendance.workers.manage` | 管理考勤档案与分组 |
| `attendance.rules.manage` | 地点、规则与生效版本 |
| `attendance.devices.manage` | 终端配对、撤销 |
| `attendance.credentials.manage` | 发卡、挂失、重置 PIN |
| `attendance.location.view` | 必要情况下查看精确位置，敏感 |
| `attendance.audit.view` | 查看考勤审计 |

默认角色模板：员工仅本人；店长仅明确授权地点／员工；考勤管理员可管理企业考勤但不自动获得订单、会员或工资权限；企业主拥有本企业管理权但仍留操作记录。

范围独立于任务看板。已明确语义：同一条授权的员工集合 AND 地点集合，多条完整授权之间 OR；禁止分别合并两个维度而产生新的员工／地点组合。采用明确的有限集合，空集合表示没有权限，缺失或畸形数据拒绝，均不解释为全企业。跨店人员的历史可见性采用可审计策略：按事件实际地点判断，不因为今日调店就自动把其所有历史交给新主管。第七批已在明细 RPC 中先限定范围再分页，并在事务内核验当前角色和授权；界面、聚合和导出仍未接入，后续同样不能依赖页面过滤。

数据库权限约束、API、角色界面、系统角色升级和权限依赖一并更新；不能只向 TypeScript 数组追加几个名称。已有自定义角色默认不自动增加敏感权限。

## 15. 实体设备与卡片选型验收

购买前逐项确认，不先承诺所有品牌兼容：

1. 卡技术和频率、读出的是 UID 还是可验证凭证，是否具备防克隆需求。
2. 接口：键盘模拟、串口、USB CCID、网络 API 或厂商 SDK；读卡能力与网页接口是两回事。
3. 操作系统／浏览器、驱动、平板供电与连接、扫码器是否能读手机屏幕。
4. 厂商接口授权／订阅成本、固件生命周期、时间同步及断网记录能力。
5. 数据出境、厂商云是否强制、设备端存储保护和清除流程。
6. 读卡／扫码成功率、重复触发、恢复供电、离线重传和撤权场景。

已有门禁机的进出日志不自动视为上下班：外出取物、访客、反向刷卡、门未打开都可能产生不同含义。只有确认事件语义、方向、人员映射和供应商接口后才做适配，首期可仅作为异常核查的辅助证据。

建议先支持两条经实测路径：现有平板／电脑终端 + 兼容扫码器；指定读卡器 + 固定终端／轻量网关。网关只在硬件协议需要时安装，不给每家商户强制新增服务器。

键盘模拟读卡器接入容易，但输入可被人工模拟，不应宣称具有硬件级防伪。高安全需求另选支持挑战响应且接口允许验证的设备。

设备接入优先主动向云端建立加密连接，不为门店网络开放任意入站端口。设备密钥分设备生成、可轮换和撤销；批量事件有签名、序号和限额，但签名只能证明来源，不能保证设备从未被篡改。

## 16. 离线、弱网与故障恢复

### 16.1 首版线上闭环

网络不可靠时保留待确认操作编号；查询服务端最终结果。完全离线时提供诚实的「待提交声明／申请补正」或备用登记，不宣称手机网页已经完成可信考勤。

服务器不可用时的业务预案：门店临时登记表 → 恢复后受控导入／补正 → 双方核对。不得为维持绿色成功提示而在本地伪造成功。

### 16.2 后续固定终端离线

- 受控本地持久队列、设备身份、事件序号、客户端事件时间、最后可信校时点和接收时间。
- 保存当时凭证／规则版本；设置离线授权最长有效期限和队列上限，容量不足明确报警。
- 恢复后有限批量、幂等上传，逐条返回已接收／重复／待核查／不接受的原因；不丢掉失败条目。
- 乱序事件按员工重放校验；不能按到达顺序误判成下班后上班。
- 离线期间卡挂失／人员停权无法即时传播，补传时核查有效区间；有争议转人工，不能承诺离线即刻撤权。
- 超期、明显时钟倒退、克隆设备序号冲突、已锁月记录不自动计入确认工时。
- 断电后队列恢复和重放通过实机测试后，才能标注该设备支持离线。

原生手机 App 离线是另一项能力，不因为某竞品支持就宣称现有 Faolla 网页也具备相同可靠性。[Factorial 手机离线说明](https://help.factorialhr.com/en_US/time-tracking/how-to-clock-in-and-out-offline-mobile-app)

## 17. 数据设计与服务端事务

以下为实体设计，最终表名与拆分在迁移评审确定，不一次性建完未启用功能。

| 实体 | 关键内容 |
| --- | --- |
| 考勤人员／在职区间 | 租户、稳定人员 ID、可选员工成员关系、工号、有效日期 |
| 地点／考勤组／规则版本 | 时区、围栏、入口、适用人员、审批范围、生效区间 |
| 班次模板／排班实例 | 计划起止、休息、地点、人员、规则快照 |
| 终端／凭证绑定 | 授权范围、密钥标识、卡与员工归属有效区间、撤销状态 |
| 原始打卡事件 | 企业、人员、动作、来源、权威时间、接收时间、操作 ID |
| 位置证据 | 单独敏感存储，精度、判定、保留策略、原事件引用 |
| 工作／休息时段与当前状态 | 可重建的有效时段、状态版本、异常标志 |
| 更正申请／审批事件 | 原值、申请值、原因、审批人、版本、追溯关联 |
| 日汇总／周期工时表 | 汇总指标、计算水位、规则版本、锁定与修订 |
| 通知 outbox／导出任务 | 事务关联、去重、重试、有限输出及到期回收 |

约束：

- 所有企业内关联使用租户约束，防止把 A 企业员工挂到 B 企业设备／排班。
- 卡只存必要的标识映射；低熵卡号宜使用服务端带密钥摘要／适当加密，不公开完整卡号；PIN 使用安全密码哈希，独立限速。
- 核心事件在日常业务路径只追加；删除／归档另走法律保留与审计流程。「只追加」不等于永远无法依法删除。
- 操作幂等键包含租户、操作者／设备和操作 ID；不同内容复用同一键返回冲突。
- 设备序列号去重和员工状态约束均在数据库事务内完成，不能只在浏览器判断。
- 事务中校验当前身份／授权有效性，写事件、更新状态并写 outbox；停权与写入并发要有明确排序保证。
- 事件接收成功与汇总完成分开；汇总失败能重建，不丢失已确认收据。
- 补正保留原事实，派生结果记录有效修订版本，导出注明版本。

安全边界：启用并测试数据库租户隔离策略；经高权限服务端客户端访问的路径仍须显式租户授权，不能把 RLS 当作自动兜底。普通浏览器不直接写原始事件表；Cookie 写接口有同源／CSRF 防护，所有入口限制字段、请求体大小和速率。凭证不进入 URL、分析埋点或错误日志；公开页面、CDN 和跨租户缓存不得缓存私人考勤。导入解析、导出下载、设备配对及离线批量接口分别做越权和重放测试。

建议接口分组：本人状态与打卡收据、本人历史／申请、管理端记录／审批／排班、地点／策略、终端配对／挑战／批量同步、工时表锁定／导出。普通用户接口不允许任意传 employeeId 代别人打卡；设备接口只能处理其明确授权范围。

## 18. 性能、空间与运维成本

沿用现有应用和 PostgreSQL，先不引入独立微服务集群、Kafka、每商户一套容器或长期保存定位轨迹。

具体措施：

- 考勤页面按需加载；不影响名片、产品、预约和订单的首屏包。
- 本人状态小接口，管理页服务端分页与日期边界；禁止加载全企业多年明细后前端过滤。
- 按实际查询建立租户＋员工＋时间、租户＋日期等索引，验证执行计划再增加索引。
- 聚合只处理新增事件和受影响日期，异常／通知有限批次，不定时全量重算。
- 大导出流式或分批后台处理，限制并发及重试；临时导出到期回收。
- 屏幕时钟本地运行；页面隐藏停止非必要刷新；管理概览按需／低频刷新，动态码请求只取小凭证。
- 地图仅配置或核查时加载；打卡不每次调用反向地理编码。
- 应用发布产物不携带员工数据、原始日志、导出和完整测试数据库。
- 延续当前「在线版本＋有用回滚版本」的受控保留，不因考勤新增永久多套部署副本。
- 功能日志不包含 PIN、完整凭证、精确坐标、健康信息；日志、导出、证据、法定记录分别设保留策略。

容量估算方法：1,000 名员工 × 每工作日 6 个事件 × 260 天，约 156 万事件／年；4 年约 624 万事件。这只是规划算例，不代表实际客户规模。用真实表结构、索引、聚合、数据库 WAL 和备份实测容量，不能用事件数直接保证某个 GB 上限。

峰值比均值重要：1,000 人集中 1 分钟约 17 次打卡／秒，加上重试和查询还需余量。压测在隔离环境用合成数据，同时观察订单／预约接口，禁止在生产进行未经批准的冲击测试。

候选验收目标（未实测，不是服务承诺）：

- 在确认的试点负载下，打卡服务端 P95 不超过 1 秒，正常网络端到端 P95 不超过 2 秒；定位和用户授权耗时独立统计。
- 定位等待上限建议约 10–15 秒，之后给出明确重试／替代方式，不转圈无反馈。
- 重复业务事件为 0、跨企业数据泄露为 0、已确认事件不因应用回滚丢失。
- 管理列表默认 50 条／页；导出范围与并发上限由基准测试确定。
- 记录基准负载和原有业务响应时间；出现明显回退先优化或缩小试点，不贸然扩容或放开。

监控：打卡成功率、结果待确认率、重复去重数、异常积压、聚合延迟、离线待同步量、设备时钟漂移、数据库锁等待、导出耗时、各类存储增量。告警去重和恢复通知，避免高频无用探测。

## 19. 隐私、劳动规则与数据保留

本节是产品设计约束，不替代劳动／隐私法律意见。正式使用前应由当地 asesoría／法律顾问核对雇佣地区、集体协议、劳动者代表安排和处理依据。

### 19.1 西班牙首批基线

BOE 当前合并文本第 34.9 条要求逐日记录每位员工具体工作开始和结束时间，并规定记录保存四年、向劳动者及有关代表和监察机关提供。这不等于所有 GPS、设备日志和照片都必须保存四年。[BOE 第 34 条](https://www.boe.es/buscar/act.php?id=BOE-A-2015-11430#a34)

AEPD 对法定工时记录的说明区分「履行法律义务的处理依据」和员工告知；不能简单使用一个同意复选框来为全部定位、照片或生物识别背书。[AEPD 工时记录问答](https://www.aepd.es/preguntas-frecuentes/3-proteccion-de-datos-en-el-ambito-laboral/FAQ-0311-es-necesario-el-consentimiento-del-trabajador-para-implantar-un-sistema-de-control-horario)

### 19.2 产品默认值

- 默认无持续定位、无拍照、无人脸／指纹模板、无跨企业员工追踪。
- 启用定位前展示目的、采集时点、访问角色、保留与申诉方式；设备授权提示不替代隐私告知。
- 商户的雇主／控制者职责和 Faolla 的受托处理职责在合同中确定；列明分包商、托管地区、删除／返还和跨境安排。
- 员工可查看本人记录、更正痕迹和下载资料；有受控投诉／异议渠道。
- 精确位置、离线证据、申请附件设置单独保留期；争议保全有范围、责任人和解除条件。
- 租户停用／付费到期不能导致法定记录自动清空；合同终止后的返还、删除与依法保留分别约定。
- 平台业务日志与部署垃圾回收不能触达考勤核心记录及有效备份。

这些最小化、保留期限、处理者合同和安全义务需结合 GDPR 的相应要求落实；不把本方案等同于合规认证。[GDPR 正文](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng)

### 19.3 生物识别单独评估

人脸／指纹不作为首版卖点或默认开关。需要时另行审查当时有效法律、处理依据、必要性、影响评估、非生物识别替代方案和设备方案。AEPD 2023 年相关指南当前标有「EN REVISIÓN」，不把该指南或竞品停用政策当作所有场景一律合法／违法的定论。[AEPD 指南页面文件](https://www.aepd.es/documento/guia-control-presencia-biometrico-nov-2023.pdf)

## 21. 分期交付与放行条件

### P0：设计固化与验证

交付：页面原型、字段口径、权限矩阵、状态转换测试样例、首批规则、隐私文案、设备兼容性候选清单和性能基线。

放行：明确第一批雇佣地区、人数／门店、优先入口；确认考勤-only 档案与现有会员身份边界；不依赖未经验证的硬件承诺。

### P1：可完整使用的考勤基础版

交付：

- 超级后台开通、独立权限、考勤人员／地点／组。
- 手机／网页、按需定位、门店动态码、终端工号＋PIN。
- 固定、分段、跨午夜、无固定班的记录能力；简单休息和请假区间。
- 本人记录、异常、补正审批、工时核对、周期锁定与受控重开。
- 基础汇总、CSV／打印、审计、保留策略、故障备用流程。

放行：核心 A01–A22 及其他适用项通过；试点能够完成一个完整考勤周期的收集、核对、锁定和导出。影子试算明确不作为工资依据，不强迫重复打卡造成混乱。

### P2：卡片、工牌与可靠终端

交付：已验证扫码／读卡器、工牌发放挂失、员工手机动态码、设备维护、受控离线队列和补传。

放行：每个声明支持的设备型号、系统、固件组合都有测试记录；断电、弱网、挂失、重复和锁月补传通过。硬件采购和安装另行确认。

### P3：复杂企业场景

交付按需求选择：轮班／换班、多级审批、假期与调休余额、项目工时归集、薪资系统映射、外部 API／Webhook、原生 NFC／BLE。

放行：每项有独立业务规则和兼容性验证，不因为「全行业」就一次加入所有复杂功能。项目工时不倒推员工销售额或任务绩效。

本轮不承诺未经验证的总工期。排期应拆成开发、自动化测试、实机验证和至少一个真实核对周期；硬件适配及当地规则确认是主要变量，而不是把所有工作算成一个页面的工期。

## 22. 无维护发布与回滚

1. 新模块默认关闭，不自动为现有员工建考勤记录或改变角色。
2. 数据库采用新增实体／兼容扩展；索引创建方式按锁风险审查，不做覆盖式历史迁移。
3. 本地和隔离环境用合成数据验证；如需关联已有员工或导入历史，先展示影响并取得明确确认。
4. 单一候选构建、针对性测试、授权与时间语义回归；不每次生成多套大体积重复产物。
5. 保持现有站点在线，候选验证后切流量，再对指定试点商户开通。
6. 发布后低频检查本人打卡、审批、导出和既有订单／预约／名片关键路径，不重复高频全站探测。
7. 故障优先关闭新入口或切回兼容版本；保留所有已提交事件，提供历史只读／受控补正处理，不回滚删除数据表。
8. 应用回滚前检查设备和新客户端兼容性；不能留下终端继续向不支持的新协议接口提交。
9. 考勤业务备份与应用回滚版本独立；发布产物的回收规则不能删考勤数据。

灾难恢复与普通发布回滚另行验收：上线前确认数据库备份／时间点恢复的真实覆盖范围，在隔离环境演练恢复、事件与汇总对账、凭证撤销状态重放。明确可接受的数据恢复点和恢复时长，不把「数据库已返回成功」宣传为任何灾难下永不丢数据。复用现有备份能力，避免为每次部署复制整库；新备份或保留策略变更需按实际权限和成本另行确认。

## 23. 推荐默认方案与待确认事项

推荐试点组合：手机网页＋单次定位（必要时）＋门店动态码／工号 PIN；门店没有合适终端时先使用手机并提供人工补正。固定场所优先终端证据，外勤优先明确政策下的手机申报。扫码与定位可按考勤组二选一或组合，但组合必须有业务必要性。

默认不开：持续位置跟踪、人脸／指纹、自动处罚、自动生成下班、静默扣休息、无限期保留定位、无审查的所有硬件接入。

实施前最有价值的确认项：

1. 第一批雇佣国家／地区与适用集体协议；是否主要为西班牙。
2. 企业、门店、员工规模和上班峰值；是否存在跨店兼职。
3. 首先以手机还是刷卡为主，是否已有终端／读卡器及准确型号。
4. 门店网络可靠性，是否必须第一批支持离线。
5. 补正／工时确认由谁审批，现有工资／会计系统需要什么报表。

在这些信息未齐全前，可以按上述保守默认值继续做原型与技术验证，但不能擅自启用真实员工定位、采购设备、修改既有数据或承诺所有国家合规。

## 24. 最终完成标准

“完成考勤”不是出现一个打卡按钮，而是：员工可通过约定入口可靠记录；主管能处理异常；工时可解释、可核对、可导出；跨企业和权限隔离可靠；断网和发布故障有不丢事实的处理办法；隐私、保留、设备兼容性和运维成本经过验证。

只有在相应阶段的功能、异常、数据、权限、资源及试点核对都通过后，才宣告该阶段完成。P1 完成不代表 P2 所有硬件或 P3 全部高级功能都已完成。
