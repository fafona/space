# 常规应用无维护发布

本通道为 `reviewed-application-code-only-v1`，用于已审查、向后兼容的网站代码修复。它不再为每个功能新增一个固定 SHA 的发布分支。历史预约激活、迁移、权限变更和事故恢复通道的原有规则不变。

本文描述实现及验收要求，不是“已经部署成功”的证明。实际成功以目标版本的完整 CI、服务器验收、`applicationCompletion`、发布凭证及独立只读复核为准。

## 发布范围

`release/application-release.json` 逐项列出实际在线基线到候选的全部变更，包括路径、角色、旧/新 Git blob 和文件模式。运行时源码、测试、文档、CI 与发布工具不能被通配符静默排除。清单本身由提交固定，不将自身 blob 加入自身内容。

数据库 SQL、迁移、依赖和包元数据变更、构建/生命周期脚本修改不允许进入此通道。`package.json` 仅可修改已审查的 `test` / `test:*` 脚本。邮件保持关闭，所有业务环境继承当前已验证版本；候选网站的后台任务始终暂停。预约后台仍运行原不可变应用；涉及预约服务器运行时的变更须使用工作进程感知的发布，而不是假称兼容。

先提交应用改动，再规划清单：

```text
node scripts/application-release-manifest.mjs <实际在线40位SHA> HEAD "明确的发布目的" src/...test.ts scripts/...test.mjs
```

审查输出，保存为上述清单并提交。清单中的所有变更都必须匹配实际 Git 树；不能用空清单、额外路径、改名或分类来夹带内容。明确排除尚未批准的应用变更。本次仍不发布单独延后的考勤实现。

## 源码与 CI

应用候选须来自当前正式 `main` 的精确提交，经过完整 PR 和正式提交 CI，包括全部 13 项现有必需检查。不能用本地绿色 JSON、旧成功运行、跳过的工作流或另一个提交的结果代替。

源码安装使用 `application-release-install.mjs` 的已审查原始 Git blob，固定安装至 `/var/lib/faolla-online-code/<SHA>` 的独立、完整、只读用途检出。源文件、稀疏索引与所有 blob 必须校验。引导器仅安装源码，不修改流量、数据库、后台任务或运行配置。原已部署的不可变审查器独立核对远程 CI；不复制 GitHub 凭据。

初次启用需要先发布纯工具提交，并使用 `application-release-worker-entry.mjs publish` 对当前预约工作进程执行一次有审计的源码更新。保留其原网站、应用、数据库、门禁、环境及其他全部进程。官方 CI 的真实 PM2 / TypeScript 应用验收、进程身份、单次重启、持久配置、保留凭证和自然周期均须通过。后续普通网站发布无需重启该任务；任务仅认可连续、已认证的兼容网站后继及其明确保留的回退边。

## 常规发布入口

在已安装源码目录运行：

```text
/usr/bin/node scripts/application-release-publish.mjs start <候选SHA> <在线基线SHA>
```

这会启动 `faolla-application-publish-<SHA>` 的服务器持久任务，不依赖当前 SSH 或聊天连接。主体最多 45 分钟，停止收尾有独立恢复命令，禁止自动重新启动整次发布。日志和凭证位于 `/var/lib/faolla-application-publications/<SHA>`，候选本体仍使用原独立网站目录及原全局部署锁。

每次启动使用新的私有 `attempt-UUID` 保存本次证据，旧失败日志不覆盖。资源预检在创建候选前拒绝时，条件满足后可用同一版本重新进行预检；已经就绪的候选仅进入切换，已经切换的候选仅进入收尾，不重新构建或重放激活。私有未就绪状态只能通过原构建/源码/实际进程证明后补完只读验收；未知构建结果和已经回退的失败版本不会被盲目重发。

执行顺序：

1. 验证源代码、完整 CI、清单及当前实际在线基线。
2. 固定全部历史状态文件的内容、权限和原 inode。不清除、不继续、不重标历史候选；本通道只允许自己精确的候选变化。独立的内存/磁盘检查必须先通过。
3. 验证已认证预约工作进程可识别兼容后继；独立复制并核对实际依赖，继承原运行环境，仅改变候选版本标识、端口及固定的暂停设置。
4. 运行已审查的重点测试，通过原 `npm run build`、环境、业务部署配置和包体积检查。保留可用内存至少 6 GiB、磁盘至少 20 GiB、无 swap 的门槛；构建硬限额仍为 4 GiB / 3072 MiB heap / 1 CPU / 128 tasks / 20 分钟 / 私有网络。
5. 对实际候选执行只读烟测。回环请求使用真实 `Host`、无 Cookie/Authorization、固定只读路径、完整响应体超时/大小限制；登录续期端点必须拒绝未认证用户，企业与预约 API 的授权边界及生产测试入口拒绝规则必须保持。
6. 只追加不可变静态资源，校验原配置快照，切换经过验证的 Nginx 上游。保留旧网站、回退版本、后台任务和历史资产，失败仅恢复本次拥有的原配置。
7. 保留凭证先在私有暂存目录写齐并 fsync 五份文件，再整体发布完整目录。半份暂存不是公共历史。完整凭证已发布但外部 head 未更新时，执行严格的 head-only 核对，不重放切换、SQL、重启或业务请求。
8. 确认两个公网域名、实际保留窗口、源文件、构建、运行环境、持久 PM2 配置和原预约门禁一致。观察认证后至少两个自然任务完成周期，不由验收程序发起调度写请求。
9. 写入完成记录，再使用独立只读审核 `application-release-audit.mjs <SHA>` 复核。进程 online、主页 200、CI 绿色或“恢复到旧版”都不能单独算发布完成。

## 资源不足时的旧备用进程退役

只针对明确选定、通过原完整退役规则的旧网站进程；不是删除备份或停止数据库。需要当前正式 `main`、全部 CI 通过、精确应用清单和独立安装的来源。在已安装来源中先检查，再执行：

```text
/usr/bin/node scripts/application-release-standby.mjs inspect <已审查候选SHA> <清单基线SHA> <旧备用SHA>
/usr/bin/node scripts/application-release-standby.mjs retire <已审查候选SHA> <清单基线SHA> <旧备用SHA>
```

新入口的进程内能力仅限这个明确选定的退役对象，不改变旧通道的历史 pending 守卫，不给调用方 JSON/环境变量跳过权限。必须重新核对当前站点及回滚窗口、完整进程集、源码/构建、真实 PID 出生、Nginx 全配置、连接和监听、子进程、暂停的后台任务、实际信号处理和持久化配置。任一不符不停止。执行只调用原审计退役器的单次按 PM2 ID 停止和持久化；保留所有文件、日志和进程注册。失败不自动重复停止。操作应通过服务器持久任务运行，避免依赖 SSH 连接。

合规退役会追加原保留证书，不重新发布网站。应用完成凭证仍必须指向经过验证、锚点不变的同一发布历史；只能接受 `retire` / `booking-worker` 的合法后缀，不能把另一版本、伪造证书或重新激活当成原发布。

## 中断和恢复

每次常规控制器在全局锁内记录自己新建操作目录的设备/inode、纳秒创建时间、控制器 PID/出生 ticks/命令摘要和锁文件身份。它不能借此认领任何历史事故锁。

服务器的独立 `recover` 会先取得真实内核锁，再确认原控制器已退出、原操作仍为空且身份未变，并等待本次受限构建单位停止。不能因 PID 被复用而向新进程发信号。恢复只接受本次源代码和本次拥有的配置/状态：

- 已完整上线且实际验证通过：保留新版，仅完成缺失收尾，不重复激活。
- 尚未切流量：保留旧站及私有候选/全部日志。
- 只完成了部分流量切换：核对后恢复拥有的原配置。
- 新版不能通过完整验证：仅在回退版本和凭证一致时恢复旧版。
- 任何真实所有权、数据协议、凭证或配置冲突：保留证据并拒绝猜测性重试。

成功恢复会保存闭合凭证，并将本次原空操作目录原 inode 归档至自己的操作记录目录。不会清空旧失败目录或解除别人的锁。真实回退不是发布成功。未知结果不得通过删除失败标记、换 UUID 重放副作用或修改检查门槛来伪装解决。

## 验收边界

测试包括精确范围/源文件绑定、历史规则保持不变、真实 HTTP Host 和响应流限制、完整保留历史与门禁、失败注入、完成记录与独立恢复顺序、PID/inode 复用拒绝及现有真实 CI 隔离网络/PM2/Next/数据库验收。历史 SHA 固定策略使用校验过的不可变测试资料，不再错误地把“当前已修改应用”当成历史原文件，也不放宽旧的生产准入。

首次实际应用发布还必须验证这条完整实际链路后，才能称其已在生产跑通。后续复用同一通道和清单格式；资源不足、源码/权限/协议冲突仍是必要的安全停止条件，不能承诺所有发布永不停止。
