## 这次实际验证了什么

复用207原有的合成历史排班、真实班次和批准漏卡。历史夹具不冒称真实员工过去的打卡或当时实际发布；新申请、批准、采用、决定与周期操作使用现有真实 RPC。

1. 原计划首段存在迟到触发。按真实选定工作端点申请并批准首段请假后，迟到变为 `not_triggered`，原始时间差归零。
2. 尾段原本差5分钟，但已在10分钟早退宽限内，原状态就是 `not_triggered`。批准尾段请假后验证时间差归零，**不称原早退异常被解除**。首尾批准覆盖之间仍有一段需出勤区间，没有把部分请假当成整段无需评价，也没有覆盖真实工作。
3. 实际负责人页面重新读取当前依据，明确选择 `cleared` 并确认提交；取消确认不产生业务 POST。使用浏览器生成的原操作编号，真实 handler→service→SQL 保存结果。
4. 实际员工页面只展示保存时依据；`current=null`、`currentValidation=not_checked`，不把历史证据冒充当前重算，也不把查看当本人已读或周期确认。
5. 用真实周期 RPC 和严格 Node 投影重新送审、本人确认、负责人封存；**此步不是点击周期页面完成**。工时合计不因请假或事后采用改变。
6. 真实取消首段请假后，当前迟到重新触发、当前案件和封存周期标记来源已变；原 `cleared`、原号回执、员工保存证据、新封存正文及先前归档的原文字节/SHA均保持。封存后的新决定被准确拒绝。

## 失败定位与窄修

本次实际运行共3轮：首轮失败日志丢失AggregateError内层信息，第二轮补充有界诊断后定位到旧整行比较误报，第三轮成功。

根因是新夹具旧行快照继承既有测试库 `Europe/Paris`，比较事务却设置UTC；`timestamptz` 经 `to_jsonb` 后同一时刻出现不同偏移字符串。171采用操作账本仅INSERT，且有不可变触发器；不能据此放宽旧行保护。新夹具现统一快照与两条执行路径的UTC/ISO序列化，并检查schema限定函数不会改写快照字面量。没有改集群时区、旧 `d.exec`、业务SQL或任何旧记录。

两次失败均执行父级清理、基线检查和停库；没有通过忽略断言、重写旧记录或延长超时来获得成功。新增诊断和时区回归计入上述28项。
