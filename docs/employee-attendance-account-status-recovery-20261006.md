# 第194批：失去员工页权限后的原账号操作核验

2026-10-06。本地实现与限定综合验收完成；未部署、未连接生产、未修改真实用户数据。不是整体考勤计划完成。

## 本次交付

193的原号GET已经允许同一真实Auth的操作者读取历史最小结果，缺口在于原员工管理页失去查看权限后不可达，独立恢复页又没有识别第三类pending。本批复用原 `/enterprise/attendance-recovery`、强认证及193客户端，增加账号停用／恢复原编号；不更改 SQL、账号状态写入、旧两类审批委托恢复协议或权限。

用户路径是：原标签页企业选择 → **核对未确认考勤操作** → 显式查找 → 选择一个原编号读取。仅处理当前身份在本标签页保存的编号，不查全企业记录、不自动重发操作、不恢复修改资格。后台原号回执仅证明原操作，不能代替“当前账号可用”“考勤已恢复”“新PIN已签发”或“新委托已授予”。

同一色块及选择列表区分漏卡委托、请假／工作安排委托、企业账号状态三类。只在完整回执、指纹、原存储字节、当前身份及页面生命周期都匹配时清除该一个待确认标记。查无回执、网络错误、换号、失效身份、隐藏或本地记录变化均保留，不做批量清理。详见[实现契约](employee-attendance-account-status-recovery-contract-20261006.md)。

## 验收中发现的测试环境问题

首次启动停在缺少 `pg_notify`，控制文件仍显示正常关闭。检查后仅补回明确测试目录内12个缺失的标准子目录，未覆盖／删除数据文件，未重建数据库。无法仅凭这一现象确定目录缺失原因。[PostgreSQL 15备份说明](https://www.postgresql.org/docs/15/continuous-archiving.html#BACKUP-LOWLEVEL-BASE-BACKUP-DATA)指出部分运行时子目录内容可在启动时重建，但目录本身仍需保留；这不是对业务库做同类修复的授权。

第二次综合运行在旧191恢复夹具的角色恢复断言中止。193已安装真实企业角色touch触发器，撤权及恢复权限会正常推进版本和更新时间，旧夹具“只恢复permissions后所有字节相同”的前提不再成立。已把旧191浏览器放回其原准备阶段；194专用夹具保留真实触发器，严格检查两次版本推进、原权限恢复，以及其他角色／业务事实不变。没有关闭约束、篡改时间或降低核验GET零写要求。

第三次运行发现实际员工身份Manager会读取通知，而原193负责人身份不会走同一员工通知分支。新增夹具端口沿真实通知处理器鉴权，仅将本包范围外的通知存储明确置为503；与原当前操作503一样，不伪造成功、未禁用页面功能，也不宣称该通知读取已经验收。随后复跑完整主链。
