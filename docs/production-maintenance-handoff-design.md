# 生产维护交接设计草案

状态：**Draft — not implemented（尚未实现）**。

本文只提出受控停机、验证与发布的设计，不是维护执行记录、停写证明或发布批准，也不表示已经停止服务、执行迁移或完成部署。不得把本文、人工勾选或文件存在本身作为维护证据。

## 1. 目标与最小范围

采用“先验证并冻结旧运行身份，再停止旧 Web 与独立 worker”的真实维护交接，替代维护期间必须继续运行旧 Web 的假设。同一旧 Web 内嵌预约定时器，停止其实际进程树可以终止该定时器，无需先发布一个兼容 bridge，也不依赖 Kong 插件热加载能力。

本次仅建设三个受审计操作：进入维护、检查维护、显式结束维护。所有操作使用固定实现和参数契约、既有 SSH 主机身份验证及发布并发组，不提供任意远程命令入口。

公网业务与登录入口在维护期间拒绝访问；Supabase 普通客户端入口也必须封闭。控制面的真实数据库健康检查、预约持久化只读检查、备份与迁移连接保持可用。具体入口控制方式依据正在进行的拓扑盘点确定，不预设插件存在，不改动未知服务。

Supabase 相关容器、独立写入者、定时任务及 prepared transaction 的精确边界由该次盘点决定。这是确定目标清单的有限工作，不要求先完成所有外部能力、所有业务页面或全平台联网验证。

## 2. 受控流程

1. **准备并冻结身份。** 在任何环境修改、目录切换或停止操作之前，验证旧 Web 的真实健康与构建身份，冻结当前发布目录、构建文件、环境文件、PM2 所有权、包装进程及实际监听进程的身份；记录独立 worker 原运行状态。工具代码必须来自已审核的精确提交。
2. **进入维护。** 先封闭已确认的普通访问入口并核实规则生效，再按冻结的身份停止 worker 和 Web。停止操作有界，逐步复验身份，不使用进程名模糊匹配或停止所有服务。停止完成后核实原进程树退出、PM2 不会立即重启、业务监听消失，且没有替代进程重新启动同一应用。
3. **形成停机证据。** 检查已识别业务写入者的在途数据库事务及 prepared transaction。只有入口、进程、运行目录与数据库边界均符合预期，才能把状态推进为 `held`。等待超时或出现无法归属的相关写入，不得签发成功。
4. **在维护持续期间执行原发布链。** 备份及恢复演练、迁移预检和应用、数据库 readiness、发布部署继续执行；每个关键边界重新检查维护事实，并绑定同一维护操作。主分支精确提交、CI、备份证明、迁移登记、数据库身份及锁检查均保留。
5. **启动并验证候选版本。** 公网入口仍关闭。只启动精确候选 Web，保留真实本机健康、构建、资源与持久化检查。新 Web 内嵌定时器需要识别维护状态并暂停每次 tick；独立 worker 暂不恢复，避免健康验收期间重新引入普通写入。这个小接点在最终应用中实现，不需要先向旧应用部署 bridge。
6. **显式结束维护。** 候选身份与验收全部通过后，以同一维护操作显式解除后台暂停并恢复预期 worker，再开放普通入口并完成真实公网 smoke。恢复顺序及失败补偿必须固定。最终公网检查失败，应重新封闭入口并转为失败持守，不记录发布完成。

维护超时、控制任务退出、SSH 断开、部署失败或证据过期，都不得自动解除维护。

## 3. 证据与验证边界

建议使用独立于应用发布目录、业务 JSON 与应用快照恢复的维护状态文件。文件仅由受控维护操作写入，原子替换、严格校验权限与路径，不提供业务接口修改入口；只存元数据，不存密钥、用户数据或原始进程环境。如果应用与维护工具同为 root，文件权限不构成进程间隔离，必须明确这是可信应用代码和主机管理员的信任边界；不能声称 root-only 文件能抵抗同身份进程篡改。

最小绑定字段：

- 协议版本、随机操作标识、受控工作流身份、预期目标提交及维护范围。
- 主机启动身份、冻结时间与当前阶段；主机重启或身份改变使原证明失效。
- 旧完整构建身份、发布目录身份、构建及环境文件摘要、当前链接身份。
- Web 包装进程和监听进程的 PID、启动时钟、进程及 PM2 所有权摘要；worker 的对应身份和原运行状态。
- 已确认入口控制的规则摘要与状态、停止完成事实、相关数据库事务检查的摘要。
- 后续备份、迁移、readiness 与部署记录对该维护操作的绑定。

状态文件不是授权，也不是持续停写的替代品。每次检查都要重新观察入口控制、实际进程、监听、目录和当前阶段。不得把历史 PID 已退出等同于应用现在没有新 PID；也不得把旧 PID 被复用的其他进程作为停止目标。

阶段检查必须区分：`held` 不允许 Web 或业务 worker 存活；候选验证阶段只允许记录中精确绑定的新 Web，后台业务仍暂停。不能用“候选允许运行”的例外放行旧 Web、未知进程或提前恢复的 worker。

对外证据只发布固定元数据及摘要，受发布链的来源与完整性校验保护。状态损坏、丢失、被替换、绑定不一致或证据过期时，检查失败，已有维护控制继续保持。

进程退出并不撤销已被数据库接受的语句、prepared transaction 或已提交给邮件服务的请求。数据库应在已识别业务边界内确认平静；已接受的外部请求只能注明原操作结果可能仍需核对，不能宣称已经撤销。不要把无关服务的常驻连接误判为必须停止的业务事务。

## 4. 现有实现的最小改点

下列位置用于划定改动，不要求维持错误的“旧进程仍活着”事实，也不得简单删除保护条件。

| 位置 | 建议改动 | 保留的保护 |
| --- | --- | --- |
| `scripts/deploy.production.sh` 开头的旧发布身份捕获、`process-snapshot` / `rollback-snapshot` 读取 | 抽取“运行中捕获”与“已维护交接读取”两个明确分支；后者只能加载经验证的维护记录并重验磁盘身份，不能伪造 `/proc` 存在 | 旧构建、目录、环境摘要、进程环境与文件配置的一致性验证仍须在停止前完成 |
| `previous_runtime_recovery_identity_matches` | 复用其目录、链接及环境文件检查；根据切换前后阶段验证预期链接 | 文件身份、路径约束和环境防替换检查 |
| `previous_web_process_identity_matches` | 保持“同一个旧进程正在运行”的原义；另增独立的 `assertMaintenanceHeld`，不让该函数在进程不存在时返回真 | 不混淆正在运行与已经退出两种证明 |
| `capture_previous_web_listener_handoff_identity`、`stop_frozen_previous_web_bounded` | 提取可供进入维护使用的精确监听进程交接能力；先捕获再停止 | 包装进程/实际 listener、PID 复用、PM2 所有权、端口释放和有界终止检查 |
| `stop_previous_automation_worker_bounded` | 维护入口增加冻结的 worker PID、启动身份、所有权验证后再停止；不能仅依赖历史名称 | 不停止同名替代进程；准确保留原先未运行的状态 |
| `run_booking_persistence_preflight` 及其后的旧 Web 校验和停止阶段 | 维护分支要求持续停机证据，不再次要求旧 Web 存活或再次停止；真实预约 SELECT 和环境 FD 校验继续运行 | 预约数据完整性、真实连接、超时、环境摘要及 readiness fence |
| `.github/workflows/database-migrate.yml` 迁移前后旧版本公网 smoke | 改为验证绑定的维护证据、停止前构建证明和当前旧发布文件身份；公网返回维护响应是独立的维护检查，不伪称应用健康 | 预期旧版本绑定、数据库身份、预检、迁移上限、登记及迁移后数据库验收 |
| `.github/workflows/ordinary-account-cutover-readiness.yml` 与部署工作流的证据接线 | 维护声明必须对应真实维护操作；在远端检查前后核验并绑定摘要 | 精确 main、CI、备份/演练证明、来源验证、有效期和数据库 readiness |
| 备份工作流的创建与签发边界 | 验证维护状态在备份及证明签发期间持续有效，记录同一操作绑定 | 一致性内容证明、加密、实际恢复匹配及清理失败不能成功 |
| `rollback_release`、`cleanup_failed_build` 及 pre-forward recovery | 为受控维护添加“停止候选、保留维护”的失败分支；必要时可还原目录链接，但不自动重启旧 Web/worker | 精确候选停止、文件恢复、锁清理与失败如实报告 |
| 最终应用的预约 tick 与独立 worker 启动 | 维护阶段阻止新的后台业务工作；新进程启动时也读取状态 | 候选 Web 可执行真实健康检查，维护结束后才恢复后台业务 |

现有旧进程检查在部署脚本前段多次直接出现，不能只修改末尾停止函数。实现时应统一到两个明确模式的共享验证入口，避免遗漏早期环境捕获或失败恢复分支。

## 5. 不改变的发布保护

- 不伪造健康响应，不把维护页当作旧 Web 的健康成功。
- 不跳过实际 Supabase 健康和预约数据检查；控制连接采用仍可用的受控内部通路。
- 不取消迁移预检、数据库锁、登记、备份/恢复证明或精确提交门禁。
- 不把已有 readiness 数据库锁误称为对全部业务写入者的全局停写锁。
- 不允许重试时凭新参数覆盖旧维护操作或默默重新开放入口。
- 不重放旧迁移文件来恢复旧 writer，也不把代码目录回退等同于数据库已经回退。

## 6. 最小验收与失败处理

本地受控测试至少覆盖以下边界，再进入已授权的精确生产维护操作；不以无限增加联网验收作为前置。

1. 记录缺失、篡改、过期、主机启动身份变化或绑定错误，必须拒绝继续，且不能解除维护。
2. PID 被复用、PM2 或其他监管机制重新启动应用、旧目录/环境被替换，必须被识别；不得误杀替代进程。
3. TERM 后进程仍在、实际 listener 未退出、后台数据库事务未平静，不能进入 `held`。
4. Web/worker 确实停止后，迁移与部署能够依据维护证明继续，同时真实数据库检查仍执行。
5. 候选版本启动或检查失败，入口保持关闭；候选清理不确定时明确报错，不自动启动旧 timer。
6. 只有精确候选及最终验收成功才能显式结束维护；重复结束、其他操作标识或迟到结果不能误解锁。

失败默认进入 `failed-held`：保留入口控制和证据，明确当前停止/启动状态。迁移已经开始后尤其不能自动恢复旧 writer；只有核对实际迁移状态与兼容性后，才能选择继续向前修复或执行独立受审计的恢复操作。本文本身不批准任何上述执行动作。
