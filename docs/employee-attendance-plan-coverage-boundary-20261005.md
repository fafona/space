# 单计划关联覆盖与规则时点：调查及下一交付边界

日期：2026-10-05，第163批。承接[162单班次独立核查](employee-attendance-independent-shift-check-20261005.md)。本批为代码调查与实施范围收口，没有修改业务代码、数据库、开关、真实资料或生产环境。下述“待批准”为当时状态；用户随后同意继续，第164批已按限定范围完成[计划关联在班跨度核对](employee-attendance-plan-coverage-20261005.md)的本地实现与验收，默认关闭、未部署。正式计划开始规则政策仍未默选。

## 查明的两个不同问题

### 1. 原开班依据不能改名成计划开始依据

[133规则收集器](../scripts/supabase-migrations/202610040133_merchant_attendance_shift_rule_bindings.sql)固定真实新clock_in时的依据，政策为`clock-in-whole-shift-v1`。它使用当时的归组当前投影、组启停和来源head，且拒绝对历史事件补采；不能只把时间参数换成slot.start_at用于事后重演。

- [124组账本](../scripts/supabase-migrations/202610030124_merchant_attendance_groups.sql)保留每个组版本的command／snapshot／recorded_at，以及最多三条assign／end／cancel归组历史。组启停、归组取消并非完全丢失；历史重建必须按旧版本，不能直接看今天的active／status／ends_on。
- [127规则发布](../scripts/supabase-migrations/202610040127_merchant_attendance_rule_versions.sql)有记录时间和UTC生效时间；[129个人例外](../scripts/supabase-migrations/202610040129_merchant_attendance_personal_rules.sql)有双身份与UTC有效区间。两者限制开始前发布／批准和撤回，草稿不等于生效规则，正常接口不允许个人例外开始后再撤回。
- 这些recorded_at来自事务内clock_timestamp，不是事务提交时间。开始前记录、开始后提交的事务，在事后仅凭该字段不能证明“计划开始瞬间已提交可见”。当前共享锁只能稳定本次读取，不能制造过去的数据库快照。
- 124归组保留民用日期和时区，没有当时固定的UTC边界；事后换算依赖读取环境的时区数据。[019通用员工审计](../scripts/supabase-migrations/202608020019_merchant_enterprise_audit.sql)只保存auth_bound布尔值，不保存Auth UUID。[136排班发布依据](../scripts/supabase-migrations/202610050136_merchant_attendance_schedule_publication_evidence.sql)证明的是发布时双身份，不证明此后从未解绑／重绑。

因此，可研究“按账本记录时间重建的候选依据”，但不能称为已证明的历史开始快照。若采用提前核准并冻结计划规则，必须明确后续规则／归组／个人例外变化是否要求重新核准；提前冻结也不等于自动获得未来开始时的最终规则。真正前瞻性规则政策将涉及发布／变更协调，不能靠独立只读接口或定时任务补出历史事实，本批不自行选择或实施。

### 2. 同一排班的关联集合尚未形成完整读取路径

[137选班关系](../scripts/supabase-migrations/202610050137_merchant_attendance_self_schedule.sql)允许同一个slot对应多个startEventId。现有162读取只核对一个原班次，第一段下班早于排班结束不等于整班早退。

关系表现有主键／唯一键分别是merchant＋startEvent、startEvent、merchant＋worker＋operation，没有slot_id前导索引。按slot反查再LIMIT并不能据此保证定位成本有界。下一读取需要独立窄索引，而不是扫描商户全历史。

还须保留以下区别：

- 普通网页旧记录、另外三种打卡通路以及明确“不关联排班”均可能不在137集合中。零关联只表示“未保存明确关联”，不是没有出勤。
- 必须从slot_id读取关联，再取完整原始／核定时段；补正把区间移到slot外时仍须返回原关联，不能先按时间相交过滤，也不能自动转绑其他排班。
- 当时取消导致待核验、成功关联后后来取消是不同事实；旧unverified关系不因今天资料齐全而自动升级。
- 完整事件与可信关联可以支持字面时间核对，即使133规则缺失；反之，可信133也不能补造137关系。规则缺失不抹掉时间事实，时间事实也不能补造判断阈值。

## 建议下一次完整交付：计划关联时段覆盖核对

负责人在既有资料核查页明确选择一个已授权排班，点击读取；新增默认关闭的只读GET／RPC一次取得这个slot的明确关联集合及各原班次的完整资料，在同一新区域展示结果。不是新增无人使用的留存表，不替换旧资料、报表、工资或审批。

### 首版口径（待批准）

| 情形 | 页面行为 | 不推导的结论 |
| --- | --- | --- |
| 多个已结束关联班次 | 原始／最新已批准核定分列，对各自上下班跨度与`[slot.start, slot.end)`求交再求并集，列合并覆盖、重复相交和内部空档 | 不是净工作时长，不扣休息，不判断早退 |
| 有休息记录 | 上下班跨度仍含休息；明确标注“在班跨度”，不与工时合计混用 | 不认定休息期间实际工作或应计薪 |
| 未结束班次 | 保留真实起点与开放状态，未知终点独立显示；已闭合部分仍可核对，但不输出整班最终缺口结论 | 不用asOf伪造下班，不把尚未观察的时间算缺勤 |
| 零时长／恰好贴边 | 保留原编号和时间点；半开区间边界不产生正长度覆盖，整数微秒计算 | 不四舍五入后抹掉短时段或制造重叠 |
| 无关联／待核验／超限 | 分别解释；超限整体拒绝覆盖计算，待核验不能偷偷并入可信集合 | 不当作全渠道完整集合、正常或缺勤 |
| 计划未来／进行中／已取消 | 明确状态，仅展示有据的时间事实 | 不作最终出勤结论，取消也不删除原关联 |
| 请假、节假日、整段漏卡 | 本次覆盖计算明确标注未纳入；原资料页已有来源核查仍保留 | 不自动减免，不把独立漏卡申报伪装成137原始关联 |

覆盖一词限定为“已保存明确关联的闭合上下班跨度”，不能显示成“完整出勤率”。原始与核定分别按同一slot核对，核定没有变化时说明沿用原始，不能叠加算两次。跨夜和DST使用保存的UTC端点，不按当前时区重写历史。

### 数据与资源边界

1. 服务端独立核验当前负责人、商户、员工与排班发布依据；没有任何关联时也须授权，不能借首个138调用代替空集合授权。历史双身份不符明确拒绝，不凭姓名或当前账号合并。
2. 先按merchant→settings→worker→employee取得既有兼容共享锁，再枚举关联。沿用原锁序和超时；关联新增、下班、批准修订、取消及身份变化的竞争须实际验证，不先承诺零阻塞。
3. 可复用[138完整班次读取](../scripts/supabase-migrations/202610050138_merchant_attendance_shift_check.sql)，但不能拼多个HTTP回复冒充单次数据库观察。若同事务复用多个138，各子asOf不同，应保留它们及外层读取起止时间，不篡改为相同瞬间。
4. 初始建议最多10个关联原班次、合计2002条原事件、响应1MiB；探测多一条即完整拒绝，UI分页不放宽服务上限。最终上限须经同一10秒SQL预算的本地验收，不能为通过测试延长原超时。
5. 候选迁移仅加独立函数和关系表上的`(merchant_id,slot_id,start_event_id) WHERE slot_id IS NOT NULL`窄索引；索引按已有在线兼容方式创建并核验定义／有效性。它仍有存储和后续写入维护成本，不能称完全零成本；不复制数据库或每班完整快照，不自动清理旧资料。
6. 旧Sources请求／响应、打卡writer、规则发布与个人例外writer、补正、工资、CSV、原计算算法均不改。既有SourcesPanel仅加独立默认关闭子入口及必要准确说明，不改变旧子区含义。
7. 明确读取、无轮询、无浏览器持久存储、无新增发送／导出；换企业／员工／排班、撤权、父资料替换、隐藏／卸载必须清除旧结果，晚响应不能回显。父资料只是选择锚点，详情有自己的截止时间。

### 一次交付的验收终点

- 单slot多段、重复覆盖、接壤、内部空档、区间外补正、零长度、微秒边界、跨午夜／DST；原始与实际批准修订分列，不改原归属。
- 零关联、有未核验关联、缺规则、未结束、后来取消、来源不全和各层超限均明确，不输出缺勤／正常／迟到早退或净工时。
- 实际页面→处理器→服务→SQL，默认关闭不请求，390px布局、鉴权及晚响应清屏；不能只靠新模型成功JSON。
- 有界索引访问及必要并发锁见证；原事实／旧定义／权限不变，新增索引是明确列出的预期差异。测试只扩展相关小fixture，不重复无关全套或完整构建。
- 复用既有合成数据库，结束后基线恢复、仅清理本次有归属证明的临时对象、停止环境。真实Auth／Next／PostgREST／手机和容量仍按试点另验。
