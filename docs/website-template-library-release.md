# 网站模板库：新增表及应用发布

此步骤仅接纳 `202611100214_website_template_library.sql` 的固定 SHA-256；不接纳其他迁移、维护模式、角色扩权或业务数据修复。原 v1 代码发布规则与原 213 数据库审查器保持不变。

1. 审查从实际在线基线到候选的逐文件清单，使用 schemaVersion 3 标注独立新增的模板表。应用、依赖和迁移均绑定实际 Git blob；未知 SQL 仍拒绝。
2. 完整 PR 与 main CI。原必需检查不减少，既有浏览器作业内增加模板库电脑/手机操作，既有身份绑定 PG15 服务内增加独立模板测试库。隔离测试涵盖事务回滚、权限拒绝、CAS、重复迁移拒绝及无关数据保持。
3. 精确 main 的签名加密备份成功后，运行 `website-template-table-online.yml`，输入同一 main、当前在线基线、备份运行 ID 和 `APPLY_WEBSITE_TEMPLATE_TABLE_202611100214`。原备份来源、身份、SSH 信任、正式库核验、业务基线和公网检查全部保留。
4. 迁移前记录原 212 项登记、原函数/ACL/数据库身份、全部进程身份与环境摘要、活动版本及 boot ID。迁移持有原迁移锁、全局部署内核锁和数据库事务锁，2 秒锁等待、10 秒语句上限；只创建空模板表和追加登记。邮件与所有运行进程不变。
5. `apply-attempt.json` 在 SQL 前独占创建；未确认的提交不能重放。若 SQL 已提交而收尾中断，只运行同一源码、同一报告路径的 `verify`，重新核对原意图、登记、精确表结构及全部运行身份后补齐自己的凭证。不能删除标记、换报告重放或接受其他表。
6. 新表在回退应用时保留，不自动删除表或重放迁移。应用发布阶段无 SQL 执行权；准入、切换前和独立审计均检查新表及不可变执行凭证，同时投影并执行原 213 证明，不能忽略任何额外登记、函数/权限或数据库漂移。
7. 表完成后使用现有 `application-release-publish.mjs` 构建、烟测和无维护切换，保留原站回滚和原预约任务，观察自然任务周期，完成独立审计。
8. 审计完成后，用活动应用现有配置运行 `application-release-template-seed.mjs inspect <SHA>`。核对 10000000 方案三的六页电脑/手机游乐场设计；再以返回的 designHash 执行 `publish <SHA> <designHash>`。只新增一个独立目录条目，不写来源草稿、已发布网站或任何用户副本。固定意图 ID 加冲突忽略插入支持安全确认，发布仍要求精确版本 CAS。

以上描述是操作约束，不代表实际部署成功；成功以签名备份、迁移凭证、网站发布完成记录、独立审计和目录读回为准。
