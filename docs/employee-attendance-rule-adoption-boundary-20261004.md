## 确定的缺口

1. 现有127／129是独立候选规则账本；三层解析明确返回 `applied:false` 和 `formalReady:false`。保存、登记、预览、留存成功，都不是已经用于真实班次的证明。
2. 131可靠保存原来源字节，但归组原文只有 `detail/currentGroup`，没有归组派生UTC起止。`merchantAttendanceRuleSources.ts` 在读取时用当前时区数据生成起止，`merchantAttendanceThreeLayerRules.ts` 又核验当前日历边界。旧原文不能直接重跑今天的解析器并被称为确定的历史重演。
3. 131不含原始打卡、选定补正、整段漏卡事实，也不含最终规则解析结果／不可变算法版本。不能把缺失输入当作零，不能据此生成既有工时报表。
4. 当前打卡和报表都没有调用三层候选解析器。报表主链为 `executeUnifiedTimesheet` → 103统一报表／093版本化报表 → `parseUnifiedSource` → `parseAttendanceTimesheetResult` → `summarizeAttendanceSessionRecords`；时长计算版本不等于规则采用版本。

这是**人工模拟日期转换变化的边界证明**，不是实际tzdata升级、真实时区错误或生产故障证据。首次命令只因ESM／CJS导入形式不匹配而未执行检查，改用现有 `createRequire` 加载后通过；没有为测试改动业务实现。未启动数据库、浏览器或服务器，未输出真实资料。

合计五个实际事件INSERT位置，没有一个可直接复用的公共append函数。现有 `events_append_only_v1` 只是禁止改写／删除的触发器。事件的 `web/kiosk` 也不完整代表四个通路；定位、PIN和现场码的附属凭据在事件之后才建立。

新增事件触发器同样会改变旧成功路径，不能以“没有编辑旧函数文本”为由绕过批准。初步倾向独立版本包装器先执行原打卡RPC，再在同一事务里按完整结果调用私有绑定助手；最终锁序、错误子事务和延迟上界须通过验收才能确认方案可用，不预先保证零影响。

## 请求批准的第一步：新班次独立绑定

以下为建议，**尚未获得本批具体批准，不是执行指令**：

- 仅本地修改／验收四通路的新规则接线；新增入口默认关闭，不部署、不启用真实商户，不改变旧事件、旧工时或工资算法。
- 使用真实新成功 `clock_in` 的 `startEventId` 和原 `occurred_at` 作为班次锚点；查询、原号回放、休息、下班以及上线前已开始班次不补绑、不追溯重选。
- 第一阶段固定“实际开班时”的四项候选参考值与完整来源，整班沿用同一绑定；跨夜、个人例外到期或班中规则变更不会悄悄切换。这是需批准的新政策，不能当作现有按UTC分段预览的同义实现。
- 首次绑定保存派生UTC边界、分段／最终值、来源版本、身份、通路、算法与输入格式版本；以后原号读取返回原绑定，不用当前时区或当前账本重算覆盖。
- 员工关联快照与本次认证人分开；PIN没有员工网页登录认证人，不能把当时员工Auth关联冒充本次登录证明。不记录PIN、密钥、定位凭据等秘密。
- 规则缺失、冲突、截断和归属不明明确记录“待核验／无法可靠绑定”，不当作零、正常或默认继承；原打卡仍按原业务规则判断。原绑定缺行也不得后来用当前资料伪造补齐。
- 新增规则来源处理不得在失败时撤销已成功的旧业务子步骤或改变PIN lease语义。基础数据库故障、死锁或连接中断仍可能使整个事务失败，沿用原编号恢复；不能承诺所有基础设施故障都不影响打卡。
- 尽量复用相同来源及小引用，不按每条打卡重复保存整份来源；上限、引用完整性和原号去重要有明确测试，不自动删除旧资料。

此阶段只固定依据，**不立即根据实际打卡时规则判断迟到／早退**。迟到涉及计划开始时的规则、排班唯一关联、跨日和迟到跨规则边界等问题；固定实际开班规则不能冒充这些问题已解决。
